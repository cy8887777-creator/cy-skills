## 一、协作纪律（铁律，优先级最高）

**总纲：授权按字面算，不外推。**"可以直接改"≠"可以重启"；"改这个文件"≠"可以重构周边"。

1. **没明确说"开工/去改"之前只讨论出方案，绝不动任何文件。**"能不能/要不要/行不行"是提议不是授权；用户说"只是问/不要动"立即停止一切编辑（2026-10-08/09 两次实证：root 占位页讨论、SKILL 受众讨论）。
2. 完工自测通过即可 commit（中文 message 带卡号），不必再问；本库当前无 remote，加 remote 后 push 政策重新评估。
3. **删除/清理类操作先确认**：列清单、确认无引用、等拍板。
4. **产物工程协调边界**：产物工程（`D:\yinglongqianduanceshi\app`）非本会话独占——执行 AI 可能同时在写；动产物文件前确认无并发写（2026-10-08 venue-intro 并发实证），改完告知用户可能的交叉影响面。
5. **验收/测试时段静默**：用户手动验收期间不开 Playwright/不跑干扰性脚本。
6. 排查/分析/复盘按既有框架走（评审三层/洞vs机制镜头/四维度），禁无框架直接 grep 了事。

## 二、工卡制度

- **按天建卡**：`design-docs/workcards-YYYY-MM-DD.md`，**卡号按天重置**（1009-01 起编，不延续昨日——实证：1008 文件混入 09 挂卡被纠正 13a2ae6）。只有按天独立，才能评判"每天到底改了多少"。
- 一卡一事一验收；挂卡必带四要素（现象/根因/修法/验收）+ **机制层归属标注**（七层骨架之一，或"合理点名"并说明为何点名——1009-13）。
- **完工卡不重启**：验收欠账/新 bug 一律走**新卡**（bug 管理式），原卡保持 [x]；欠账信息只在新卡（2026-10-09 用户裁定，229b42f）。
- **发现新问题不顺手修**：输出"问题+影响面+建议优先级"，先问用户"立刻修，还是记工卡挂账？"
- 执行中撞见方案外的事（新 bug/顺手优化）：停，不扩 scope，报用户定夺。
- **工卡审核 gate（1009-20/22 配套，2026-10-09 用户定案）**：工卡挂出后必须经**工卡审核 AI**（独立子代理）审查——**审核 AI 完全同意（无任何未闭环发现）之前，禁止开工施工**。有发现 → 修订工卡 → 回派复审，循环直至完全同意（轮次不限，审到收敛为止）。复审裁定"不通过"后同理：修复不构成回填依据，回派复审确认发现逐条闭环后，方准回填完工状态。
- **工卡入 git**（2026-10-09 用户拍板，与 screenshot-to-code 的"不入库"相反）：技能要分享，工卡=进化记录与培训素材，与 design-docs 设计/演进文档配套使用；本库无开源上游，无污染问题。
- **质检裁定协议（UDP）**：全管线质检判断点的统一裁定程序——判断带对照物/对审独立/分歧仲裁（判例账本）/账本备案；四条边界：判断类型决定复核强度、原始 FAIL 不可账本改判（必须修工具或输入后重跑）、账本只记裁量（机器结果归证据索引）、冻结决定变更权限在用户。全文见 station-guide「质检裁定协议」节。
- **ACTIVE-BACKLOG.md = 活卡总表**：每轮开工必读；状态勘误职责（实证：1007-12 状态漂移靠勘误才发现，0671f00）。
- **完工闭环**：施工 + 自测（反例套件）+ 验收（分级矩阵见 §五）+ 状态回填 + commit，缺一不算完工。完工回填须对照**卡面验收条款原文**逐条核，禁按实现自写自验（实证：1008-04/09 带病完工，codex 对照卡面才抓出）。
- **完工验收分级 gate（1009-20 v3 终版）**：
  - **复杂卡（P0/新工具卡/新机制卡）：测试角色 gate**——施工前，测试角色
    （独立子代理，不看实现）根据**卡面验收条款**独立制定测试标准 → 开发 AI
    审核（仅可行性异议，覆盖点只增不减）→ **标准写入工卡** → 施工 → 测试
    角色写用例+执行 → **工卡 [x] 由测试角色打**。测试用例禁从实现推导
    （实证：1008-04/09 假绿 = 测试按缩水实现自写自验）。
  - **简单卡（纪律/条文类）**：三绿 gate = spec review（输入含卡面验收
    条款原文，禁施工者总结替代）+ 规范 review + 反例套件。
  - 点名小卡：自验+反例套件。
  - 适用范围=技能工卡完工；管线生成项目交付 gate 见 station-guide §10。

## 七、交付卫生（每卡 commit 前逐条过）

1. **入库边界**：技能文件/工卡/design-docs 均入库；临时脚本、诊断截图、个人笔记不入。**精确 add**（点名文件），禁 `git add <目录>/` 宽泛添加——实证：`git add design-docs/` 误把另一会话未提交文件带进 commit（fa092c8 已 reset 修正）。
2. **commit 完整性**：commit 前 `git status` 看含 untracked 的完整输出，对照改动清单逐一核对。
3. **同族洞排查**：修任何一处，列出同构路径逐一核对——实证：venue-intro 死端修复时全站扫描 12 张素材同病（1008-14）。
4. **交付可用性自查**：交付前自问"用户常规使用会不会撞坏"——主流程问题当场修不挂账；已知问题分级如实（blocker/major/minor/cosmetic），报告数字=最终工程态可 diff。
5. **工卡完工三查**：标题状态、正文修法、交叉引用与最终产物一致，陈旧表述当场改，不带病归档。
6. **工作流文档同步**见 §六（过时=bug）。
