# AI 辅助开发培训：一手资料核查

核查日期：2026-10-08。用途：为《设计和技能演化文档》的“方法复盘”提供外部参照。以下只引用来源明确的原始文章或官方指南；本项目成败仍以会话、Git、脚本与实际运行证据判断。

## 可以吸收的结论

1. **先发现问题，再固定方案形态。** Teresa Torres 的机会解决方案树把“预期结果→用户机会→候选方案→假设试验”分开，并明确警告不要凭空编造用户机会。适合补强现有“如何从功能想法找到真正问题”“多个方案如何决策”：先问真实用户任务与证据，再比较 Plan、技能、产品或其他载体。来源：[Opportunity Solution Trees](https://www.producttalk.org/opportunity-solution-trees/)，Teresa Torres / Product Talk。
2. **复杂编排应由任务特性证明其价值。** Anthropic 建议从最简单可行方案开始；可预测、步骤明确的任务适合 workflow，需模型动态决策的开放任务才考虑 agent。并行适合可分离的工作或需要独立视角；多步系统增加延迟、成本和错误累积。适合补强现有“Plan、技能如何选择”“何时用子代理”“怎样避免闭门造车”，但不能据此断言本项目十站是唯一最优形态。来源：[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)，Erik S.、Barry Zhang / Anthropic，2024-12-19；该文自身提示工具生态已有变化，因此引用原则，不照搬当年的具体工具选型。
3. **AI 写得连贯，不能证明它掌握了全部项目事实。** Claude Code 官方指南明确指出上下文增长会使模型表现下降，建议提供具体上下文、先探索再计划、给它可运行的检查，并让新上下文中的审查者尝试推翻结果。适合补强“为什么完整方案仍有漏洞”“如何降低幻觉”“为什么角色任务书要配发到执行现场”。需要避免把模型说成“只会生成文字、不会推理”：当代编码代理能推理、调用工具、观察运行结果；限制是其可见上下文、证据与验证覆盖不完整。来源：[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)，Anthropic 官方文档，核查时正文包含“Manage context aggressively”“Give Claude a way to verify its work”“Explore first, then plan, then code”。
4. **把结果交给独立证据。** GitHub 官方指南要求理解建议代码，检查功能、安全、可读性与维护性，并用测试和工具验证；Claude Code 指南要求展示测试输出、命令结果或截图，且建议独立审查。适合补强“如何提高代码质量”“测试全绿但用户不可用怎么办”：按风险选择检查层级，并让浏览器中的用户动作和业务结果参与验收。后半句是本项目的实跑教训，不是上述文档的原话。来源：[Best practices for using GitHub Copilot](https://docs.github.com/en/copilot/get-started/best-practices)，GitHub Docs；[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)，Anthropic。
5. **工具提速会放大原有工程能力。** DORA 2025 的报告摘要把 AI 描述为放大组织既有优势和弱点，而投资回报取决于底层工作系统。适合补强方法章节的总警示：“更多代码、更多页面、更多 agent”不是完成度；需求、工作分工、验证与交付口径若有缺陷，自动化会将缺陷复制放大。来源：[2025 State of AI-assisted Software Development](https://dora.dev/research/2025/dora-report/)，DORA / Google Cloud。这里只引用报告摘要的定性结论，不移植其统计数字到本项目。
6. **“vibe coding”存在术语歧义。** Simon Willison 梳理 Andrej Karpathy 的原始用法：让模型写代码、自己几乎不读 diff，适合低风险原型；若审查、充分测试且能解释代码，更准确地说是 AI 辅助软件开发。适合在“方法复盘”前加一段短定义或问答：本培训沿用大众叫法，但展示的是带产品判断与工程验证的人机共创。不可把作者的个人生产代码标准说成行业统一规范。来源：[Not all AI-assisted programming is vibe coding](https://simonwillison.net/2025/Mar/19/vibe-coding/)，Simon Willison，2025-03-19，文中直接引用 Karpathy 的原帖。

## 建议映射到当前问答

| 现有问答或缺口 | 建议调整 | 依据边界 |
| --- | --- | --- |
| “一次性计划、可复用流程和产品，该怎样选择？” | 用一个决策框架回答：重复频率、输入变化、流程稳定性、验收方式、维护责任。Plan 管单次执行状态；技能装跨项目可复用指令与工具；产品要有明确用户、体验和维护承诺。说明几者可组合，避免强制三选一。 | 本项目 Plan/技能争论 + Anthropic 简单优先原则；并非外部指南给出这三个选项的定论。 |
| “AI 在产品与编程工作中最擅长什么？” | 分任务说明：候选方案拓展、资料初筛、重复代码、测试草稿、代码解释与定位；每项写人需要补上的事实核查或价值判断。 | GitHub 明列测试、重复代码、调试、代码解释等；产品探索部分主要来自本项目观察。 |
| “为什么 AI 的方案写得完整，仍然会有漏洞？” | 答案从“完整文本 ≠ 完整证据”展开：未知输入、上下文衰减、错误工具使用、错误验收判据四种来源；给出每种对应检查。 | Anthropic 上下文与验证建议 + 项目中的漏站、假绿实例。 |
| “AI 搜到的资料可以直接当答案吗？” | 讲来源层级、时效、适用前提和原文核查。增加“让 AI 给出处，并追到拥有事实的原始发布者”，同时以小实验验证工程断言。 | 本轮研究本身展示了旧 URL、重定向和网页摘录可能误导；属于研究方法归纳。 |
| “如何盘问一个看似合理的 AI 方案？” | 从“追问替代方案”升级为四问：目标是什么、哪些事实未知、最小验证是什么、什么证据会推翻方案。反例是测试输入，不是辩论技巧。 | Product Talk 假设试验 + Anthropic 可验证反馈。 |
| “什么时候适合并行使用多个 AI 代理？” | 补充“是否真的有独立输入/输出与合并成本优势”。纯粹加代理数量不保证快；主会话必须持有共同状态与最终验收。 | Anthropic 并行、orchestrator-workers 与成本权衡。 |
| “怎样提高 AI 生成代码的质量？” | 增加“读懂 diff 并能解释关键路径”“真实用户流程验收”“独立审查”，把 lint、测试、截图各自能证明的范围写清楚。 | GitHub/Claude Code 官方实践；用户流程部分是项目证据。 |
| 新增：“什么时候应该停止让 AI 继续生成代码？” | 当目标或输入未定、连续补丁没有根因、验收失败被话术翻案、代码已无人能解释时，回到需求、证据或最小复现。 | Claude Code 的早纠偏、根因与验证建议 + 本项目行为证据。 |
| 新增：“AI 的效率优势在哪里会反过来制造成本？” | 同时计算生成速度、审查成本、集成成本、返工与运行验证。使用 DORA 的“放大器”视角解释规则缺失时为何会批量复制错误。 | DORA 定性结论 + 本项目 80 余页交互失效案例；不能声称 DORA 验证了本项目。 |

## 不应写成通用定论

- “AI 只是生成文字，没有真正推理或全局智能”过于绝对。更准确：输出由模型、可用上下文、工具观察与反馈共同决定；它无法天然知道项目中未提供或未检查的事实，也无法替代人确认产品目标。
- “独立裁判必然可靠”不成立。审查者也可能共享错误基准；仍需检查基准和抽样范围。
- “增加脚本门禁就能保证业务可用”不成立。脚本只证实它检查的合同；需要用户流程和结果证据。
- “Vibe coding 就是现代 AI 编程的全部”与术语原义不符。对培训对象可保留通俗标题，但正文应明示这里采用更宽的口语用法。
