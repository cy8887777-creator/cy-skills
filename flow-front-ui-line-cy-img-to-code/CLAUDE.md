## 一、协作纪律

**总纲一：授权按字面算，不外推。**"可以直接改"≠"可以重构周边"；"能不能/行不行"是提议不是授权；用户说"只是问/找原因/不要动"→ 停止一切编辑，只输出结论。

**总纲二：PASS 含金量原则（本技能一切纪律的源头）。**模型信任脚本的 PASS 是义务——脚本放行的一切必须可信；检测器"拿不准"必须 REVIEW。坏→OK 的成本（终局穿透）永远高于误报→REVIEW（多看一眼）。强化技能时的每一张卡都在为这条原则服务：检测器改动问"会不会假绿"，新机制问"软路径还是物理拦截"（提示词要求无效，唯一有效处置：管线物理产出 / FAIL 闭环 / 白名单）。

## 二、工卡制度

- **按天建卡**：`.scratch/workcards-YYYY-MM-DD.md`，卡号按天重置（当日 1009-01 起编）。
- 一卡一事一验收；挂卡必带**四要素（现象/根因/修法/验收）**+ **机制层归属**（七层骨架之一，或"合理点名"并说明）+ **根因定性**（设计缺陷/执行偏差/认知盲区——三者修法不同，禁混）。
- **完工卡不重启**：验收欠账/新 bug 一律走新卡，原卡保持 [x]。
- **发现新问题不顺手修**：输出"问题+影响面+建议优先级"，先问用户"立刻修，还是挂卡？"
- **工卡入 git**：工卡 = 技能进化记录。
- **验收标准先于施工写入卡面**；完工回填对照卡面验收条款原文逐条核，禁按实现自写自验。
- **完工验收分级 gate（源自 design-pack 假绿教训，完整采用）**：
  - **复杂卡（P0/新工具卡/新机制卡）：测试角色 gate**——施工前，测试角色（独立子代理，不看实现）根据**卡面验收条款**独立制定测试标准 → 开发侧审核（仅可行性异议，覆盖点只增不减）→ **标准写入工卡** → 施工 → 测试角色写用例+执行 → **工卡 [x] 由测试角色打**。测试用例禁从实现推导（实证：按缩水实现自写自验 = 假绿）。
  - **简单卡（纪律/条文类）：三绿 gate**——spec review（输入含卡面验收条款原文，禁施工者总结替代）+ 规范 review + 反例套件。
  - 点名小卡：自验 + 反例套件。
- **完工闭环**：施工 + 自测（含应 FAIL 反例）+ 验收（分级 gate）+ 状态回填 + commit，缺一不算完工。
