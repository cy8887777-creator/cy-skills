# 九段共创玩法手册（候选生成规则 / 应答模式 / 回流）

> 配合 SKILL.md 九段表使用。本手册写每一段的**生成规则、渲染形态、落锤动作**。
> 交互性质三类：**确认型**（单卡展示，回复「可以」或指出要改哪里）/ **选择型**（4 个候选双列，回复「选 N」/多选排序/「再来一批」）/ **版本型**（样品页 3 版机制，看版定案）。

## 通用应答模式

| 用户动作 | 处理 |
|---|---|
| 文字新想法 | 「要更年轻」「再克制点」「霓虹感重点」→ AI 翻译成参数/检索词变化，更新候选——**一等公民，不是异常** |
| 贴参考 | 发链接/截图 → 提取特征并入候选（链接先实测可达） |
| 委托 | 「你定」→ 落推荐项，看板标【AI 代定】 |
| 回改 | 任何已答步骤可重开；向下游发**软提示**（建议重看某步），不自动作废 |
| 再来一批 | 候选全不满意 → 换角度重生成；风格库全不贴 → AI 自创（完整描述+标【自创·演化自 xx 家族】，规则见 concept-boundary） |

## 候选生成前置 · 约束回读（防决策链失忆，违规即返工）

> 连续多步共创中，执行者必然发生「决策链失忆」——上一步落锤的约束在生成下一步候选时被遗忘。自举项目实测暴露此模式（风格落锤后组件样张无风格痕迹、四库样张参数化趋同肉眼不可辨）。防法是流程化，不靠自觉：

1. **生成候选前回读已锁决策清单**：外部输入约束 / 风格定义 / 已落令牌 / 历史否决项——逐条问「本步候选如何体现它」
2. **候选卡必须可见地体现至少一条已锁约束**：视觉上看得见（如样张中的风格锚、令牌上色、已认形态语言），不是文字里声明一句「已考虑」
3. **参数化模板禁令**：同一步多张候选若用同一模板仅换参数（radius/色值/密度），视为趋同不合格——候选间必须有**结构或形态级差异**（不同控件种类、不同分层策略、不同布局骨架）
4. **与已锁决策冲突的候选直接返工**（如清新约束下出深底卡、文档流已认后出网格卡、纯黑已否后主按钮用近黑）

## 第〇步 · 原型画像（确认型）

- **机制**：`scripts/content-dump.mjs` 转写内容清单 → `scripts/build-manifest.mjs` 建索引 → AI 汇出画像 → 人话画像卡（这是什么产品/几页/什么端/做什么/约束）→ 用户确认或纠正
- **落锤后**：画像写进决策链；布局归类成为「布局」章底稿

## 第一步 · 外部输入（确认型 · 收料展示）

- **时机**：第一步。用户手里的图片 / token / 品牌素材 / 竞品参考 / 想法描述——先收进来，作为约束注入画像与后续所有候选
- **机制**：材料先做可用性检查（图片可读 / token 结构 / 链接可达）→ **每条提交一张解析卡**（色卡提色块 / 截图与 Logo 缩略描述 / 文字提示原文引用块）→ 多次提交多条 → 影响后续每步候选生成与过滤
- **索要引导**：卡尾常驻「还可以补充：品牌色卡 · Logo · 截图 · 竞品 · 文字要求」；没有则说「跳过」，不强制

## 第二步 · 风格定义层（选择型 · 4 候选 · 单选整卡）

- **候选来源两轨，禁止机械照搬**：①风格库（design-style-wiki `atlas/cards`）按画像三键检索（行业品类 best_for / 气质 / 载体端向）——库内卡必须经**画像适配演化**（结合已认方向与外部输入重写「适合理由」与实现层要点，不是复制粘贴卡原文），**引用必标卡 id**；②库不贴或已认方向需要正式化 → **自创**：按 wiki 描述标准写全 + 标【自创·演化自 xx 家族】——**自创不回流风格库**。两轨同场竞争，用户在完整描述之间选，不标"哪个来自库哪个自创"的歧视性排序
- **候选数量弹性**：4 张为基准，风格空间大或用户要求时可出 5~6 张
- **候选标准**：每张 = 完整风格描述——概念（是什么、像什么）/ 观感话术 / 家族归属 / **适合本项目的理由**（对照画像业务域与体验意图）；四要素缺一不合格，裸配色方向不合格。探测 wiki 在位（`atlas/INDEX.md`）才启用库检索；缺位 → uupm styles.csv + 自拟（标【AI 自拟】）
- **硬边界**：单选一张卡整卡执行，禁止组合混搭；数值只能来自卡（自创卡禁数值）；详见 references/concept-boundary.md
- **渲染**：风格卡（名称 + 家族 + 观感话术 + 概念段 + 适合理由 + 实现层要点；库内卡带血统标注行）
- **应答**：回复「选 N」（**单选整卡**）/ 多选仅作偏好排序 / 「再来一批」（换角度重新检索或重自创）
- **落锤后**：总览「设计价值观」章填充 = 选定卡完整风格描述与血统（章内「风格定义」小节）；**该卡实现层成为第三步令牌底座**（第三步 = 风格骨架 × 业务微调 + 语义化补全，styles.csv 检索降为交叉验证）

## 第三步 · 设计令牌（选择型 · 4 候选 · 只有颜色/字体/字阶）

- **拼装规则**：
  0. **第二步选定卡实现层为底座**（库内卡照卡 §3/§4 要点；自创卡按家族锚从库检索相近风格成熟方案）——本步 = 风格骨架 × 画像业务微调 + 语义化补全
  1. styles.csv 关键词检索**降为交叉验证**：佐证底座方向有无成熟方案；冲突以选定卡为准并在候选卡标注差异
  2. 底座 + 画像类型 → colors.csv 匹配语义六件套。**主色被外部锁定时不得跳过本步**——用锁定主色（或邻近色相）检索 colors.csv 取成熟配色方案，语义色/状态色/底面边框取值从方案来；同时检索 styles.csv 配色体系与品牌 DESIGN.md 色板结构做层次参照
  3. 选定卡字体倾向 → typography.csv 筛字体配对
  4. **配色策略必须拉开**：主色锁定只锁品牌主色，不锁搭配策略——候选间至少覆盖 3 种配色策略（同色系层次 / 撞色强调 / 邻近色协调 / 双色调），每卡标注策略类型；撞色等风格搭配是合法且被鼓励的探索方向
- **边界**：令牌卡只有**原子规格**——语义色板 / 状态色 / **色彩层次（灰阶 8-10 档 + 主色/强调色 ramp + 状态色场景）** / 字阶真渲染。**圆角、阴影、组件的形状样式不在此步**——那是第四步按组件库基调判断的事
- **色彩层次按 data/refactoring-ui/05-color.md 方法构建**（灰阶 8-10 档带温度饱和 · 主色 5-10 档 ramp（base 以能做按钮底实测）· 强调色各带 ramp · 建梯 900/500/100→700/300→800/600/400/200 · 饱和度向两端补偿 · 色相旋转 ≤20-30° · 状态签翻转对比 100 底+800 字）——只有单一主色+中性灰的候选不合格
- **渲染**：4 张方向卡双列，每卡 = 原子规格卡（无组件样张、无形状）
- **落锤后**：总览颜色/字体章填充；推导项（状态色/图表色）实时写进对应章节与决策链

## 第四步 · 组件风格（选择型两层 · 形态来自库）

- **第一层 基调库形态卡**：候选 = data/component-styles 已快照库（按画像端向挑），每张卡内画**该库官方形态的核心组件组合样张**（形态是库的，不是我们发明）——用户选一个基调
- **第二层 逐族规范过目卡**：基调形态语言 × 已锁令牌上色 → **按原型实际组件清单逐族过目，禁止自定三五族截断**（回读 chapters.md 组件章覆盖标准：原型实际 ∪ 常用标准件 ≥20 组）；过目卡 = **大卡规格书格式**（对齐实战产物）：每组大卡头栏带来源徽章、变体行、**状态穷举实物（交互组件 ≥三态）**、真 HTML 控件；次级组件（徽标/空态/分割线/头像）从已选派生，聚合过目
- **落锤后**：总览组件章按族填充；圆角/阴影章从基调规格派生成文

## 第五步 · 图片素材（确认型 · 单张策略卡 / 无图可跳过）

- **第〇问 · 需求判断（先于能力探测，违规即返工）**：从画像与已落决策推导——这个项目的界面**有没有真实图片位**？逐位列出（摄影/插画/空态/氛围/封面）并验证。**无图位 → 落「无图策略」直接跳过本步**（保留一句：未来出现图片位按兜底策略执行）。禁止在无需求时产出策略卡、禁止为填卡虚构用途
- **有图片位 → 探测本地生图能力**（solo-img-line-cy-bailian-image-gen 等技能/工具存在性）：有 → 策略卡写明生图主用；无 → 告知并给三条路：跳过占位 / 用户提供图包 / 纯色卡片占位
- **渲染**：单张策略卡——图片位清单 + 能力探测 + 来源策略 + 风格要求 + 禁止清单
- **应答**：回复「可以」或直接改策略
- **落锤后**：图片策略写进决策链；总览图像章填充

## 第六步 · 图标（选择型 · 4 候选）

- **候选**：开源图标库风格卡，**每卡几十枚真实 SVG 图标墙**（不是三四枚示意）+ 分类统计（哪些类目图标多、业务特形图标缺什么）+ 查看链接（本地 data/icons-json/ 十库离线可用）
- **双形态**：同库有线性和面性两种形态的一并展示；不同库的画法差异要画出来
- **特殊路径**：用户选 C4D/3D 类 → 确认风格关键词 → 生图能力探查 → 生成一批图标样式样例
- **独立性**：SVG 图标用 currentColor 渲染，与颜色/圆角无关——本步时序自由，不依赖第二步排序
- **落锤后**：总览图标章填充（风格/来源/尺寸规则/双库分工规则）

## 第七步 · 查漏（确认型 · 单张盘点卡）

- **机制**：对照 references/chapters.md 章节模板逐章检查待定项——能推导的当场推导写进决策链，需要用户信息的一次性补问
- **盘点粒度：两级（章级 + 卡槽级）**——只盘章级有/无不够：每章还要对照 playbook「必备卡槽核对」清单盘**卡槽级完备性**（该章该有的实物卡槽——色板墙/字阶行/间距尺/圆角盒/阴影卡/组件舞台/图标陈列/PROMPT 母版——齐不齐、来源角色标了没）。**缺失内容补充发生在本步**：卡槽缺口当场推导补齐或标 AI 补全角色；第九步成文只做按 case 底稿复写，不再发现新缺口——成文时还在补内容 = 查漏失职
- **渲染**：**单张盘点卡**——逐章核对（章级 + 卡槽级两行），缺口标「补」、维持结论标「确认」
- **出口**：全部章节章级非待定 **且** 卡槽级齐备 → 进入样品页

## 第八步 · 样品页（版本型 · 每页 3 版）

- **页单**：按**画像页面清单**的代表页生成（页数页名画像已定，不问）
- **跑批**：每页 3 版，不同子代理独立制作；子代理指令 = 定稿规范 + 代表页转写要求 + **诠释策略**（版1 严格遵循 / 版2 规范内均衡 / 版3 反向试探）
- **质检前置**：每版交稿先跑确定性质检（截图 + 规范符合度 / 可访问性 / 断图 / 溢出检查）——质检问题派回子代理修复并复验，**质检过的版本才进看版**；用户看版只做主观定案，不被低级问题干扰
- **渲染**：3 版并排，每版带页面样张
- **看版硬标准**：①色彩节奏——运用色彩层次（tint 梯分区/图标底/状态色点缀），全页白底+单一主色不合格；②图片位——代表页关键图位配真实图或带构图说明的高质量占位，全页无图不合格；③诠释差异在结构之外还要体现视觉手法差异；④业务内容真实（无占位假文）
- **看版**：用户选一版或拆吸收
- **回流**：定案版处理细节以【定案版回流】补进对应章节（决策链与章节内容同步更新，不改已锁决策本身）
- **验收**：回流后渲染代表页整页 → 用户过目

## 第九步 · 收尾（成文型 · 章节成文与审阅 + 导出）

- **时机**：样品页定案回流之后——成文必须反映回流后的最终状态
- **成文前必读（防标准失忆，违规即返工）**：①先读 **`references/case-guide.md`（案例导读 · 结构地图，5 分钟）**——骨架三层/15 章卡槽清单/block 词汇表/组件大卡解剖/背景四落点/成文对照工作法全在导读里；按图索骥查 `data/case/design-system.case.html` 对应章的完整写法。**章节内容必须达到案例的可视化丰富度，摘要级 HTML 不合格** ②重读 SKILL.md「预览章可视化铁律」与导出标准。**长流程末端上下文失忆是实测病理**（自举项目第九步曾以摘要级 HTML 导出 23KB，case 基准 1.8MB）——主会话上下文已超长时，**成文必须派子代理**（任务书喂 case 导读 + 定稿链数据 + 14 章规划），主会话不亲自成文
- **卡槽来源角色标注（case 规矩 · 每个卡槽必标）**：每章的每个数据块必须用 role-badge 声明来源角色——**实测**（用户拍板/库卡引用/画像实值）/ **AI 补全**（派生值、建议档、断点推导）/ **引用**（通用规则模板）。AI 补全值禁与实测混排（禁令⑩：禁把 AI 补全值当实测引用）。漏标角色的章不合格——消费方需要知道每个值可信度几何
- **复写方法论（solo-ui-line-cy-design-system-extract 技能 gen_html 同款 · 模板是带答案的底稿）**：case 成品 HTML = 完整案例字面（色板卡/组件实物/表格数值全是"标准答案"）。成文 = **以 case 对应章为底稿逐段复写**：复制它的 block 骨架与交互代码（data-hex 点击复制/字阶行/组件舞台），把演示值逐段替换为本项目实测值——**禁止脱离底稿从零自由发挥**。脚本（export-clean）只做程序化区域：:root 皮肤变量 / hero-meta / ch-intro / 版本日期名。导出后必须跑**品牌污染扫描**（export-clean 内置：case 品牌值残留非零即 FAIL）
- **视觉自证前置（文本门禁过 ≠ 能交付）**：门禁断言只能证明结构存在（字符串命中），证明不了视觉正确——玻璃可不可见、按钮是不是真渲染、排版像不像 case，**字符串全命中也可能是错的**（自举实测：ds* 类无样式散架、玻璃在纯色底上隐形、按钮裸 CSS 三事故全是文本验证漏网）。交付前必须**渲染目检**：①首选派独立子代理（新鲜眼睛）打开产物逐屏对照 case 样张，报告玻璃可见性/控件真渲染/排版对齐——不得只做结构校验；②或走 solo-ui-line-cy-ui-walkthrough 走查。目检 PASS 才能 present 给用户。**交付承诺 = 验证责任在执行方闭环，用户只做主观定案不做 QA**；渲染手段不可用时的降级（几何核算/结构校验）必须如实声明「未经视觉实证」
- **必备卡槽核对**（对照 case）：色板墙（点击复制）· 字阶真渲染行 · 间距尺 · 圆角盒 · 阴影卡 · **组件大卡**（来源徽章+状态穷举+真控件，非装饰 span）· 图标实物陈列 · **PROMPT 母版**（图标库缺货时的生成提示词模板，pre 代码块）· 各章 ch-intro（export 模板内置）· **组件章覆盖度 ≥20 组**（原型实际 ∪ 常用标准件，章 11 专项核对）· **背景贯穿四落点**（颜色 bg 槽位唯一性 / 布局底色原则句 / 间距白卡秩序机制句 / 禁令背景唯一性——背景不单独成章，按职责拆进各章）
- **机制**：按章节模板逐章成文（布局归类/组件契约/多端/禁令业务补充/动效占位）→ 用户审阅（轻确认，可聚合审）→ 导出纯净版（system-rules.md + spec HTML）
