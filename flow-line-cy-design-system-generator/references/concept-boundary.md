# 第二步 · 风格定义层的硬边界（违规即返工）

> 风格定义层候选 = **完整风格描述**（概念是什么 / 观感像什么 / 家族归属 / 适合本项目的理由）。
> 来源两轨，纪律不同：
> - **库内卡**：从风格库（design-style-wiki `atlas/cards`）按画像三键检索（行业品类 best_for / 气质 / 载体端向）——**引用必标卡 id**；实现层数值（hex/字体/圆角）来自卡、合法。
> - **自创风格**：库不贴时允许——必须按 wiki 描述标准写全（概念/观感/家族归属/适合理由），标【自创·演化自 xx 家族】；**自创卡禁止出现具体数值**（hex/px/字体名）——AI 发明的数值不可信，令牌值第三步从库检索相近家族的成熟方案做底座。
> - **自创不回流**：自创风格只活在当前项目的决策链与设计系统里；风格库的生长走它自己的采集→对照→转正流程，两者完全隔离。

## 铁律（违规即返工）

1. **单选一张卡整卡执行，禁止组合混搭**——候选之间是并列选项，落锤后不允许「A 的排版 + B 的配色」式拼装
2. **数值只能来自卡**：库内卡的实现层值照卡执行；自创卡禁出现具体数值（生成后自检：扫 hex `#[0-9a-fA-F]{3,6}`、px、字体名，命中重写）
3. **引用必标血统**：库内卡标卡 id（如 `glassmorphism`），自创标【自创·演化自 xx 家族】
4. **描述必须完整**：概念 / 观感 / 家族归属 / 适合本项目的理由——四要素缺一不合格；**裸配色方向不合格**（只有配色气质没有形态语言的候选打回重写）
5. **候选渲染前实测可达**：引用的卡必须存在且 `card.md` 可解析

## 与第三步的衔接

- **库内卡落锤** → 该卡实现层（颜色/字体/圆角/阴影倾向）成为第三步令牌底座：第三步 = 风格骨架 × 画像业务微调 + 语义化补全（状态色/字阶/灰阶层次），styles.csv 检索降为交叉验证
- **自创卡落锤** → 第三步按其家族锚从库检索相近风格的成熟令牌方案做底座，业务微调同上
- **wiki 完全缺位** → 第三步回退 uupm styles.csv 主检索拼装（原路径），选定风格描述仍作为气质锚
