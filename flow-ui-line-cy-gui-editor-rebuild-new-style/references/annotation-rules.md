# 旁批行文规则

写每页旁批前把本文通读一遍；落笔后只对照「落笔后检查」逐项过。

> **立意**：旁批是产品经理站在页面旁边，给看原型的人讲功能——讲的是**界面背后的东西**（需求逻辑），不是实现方案。
>
> **总纲**：判断标准只有一条——看产物的人能不能顺畅理解这个功能怎么运作。

## 行文规则

1. **站在整个项目写**：按页组织，但业务逻辑贯穿——每页写清它在链路里的位置（入口从哪来、操作后去哪、同一规则还在哪些页出现）；同一规则多页出现时口径一致，高频主路径页可当场重讲，不能每页全文复读。
2. **开篇点题**：每页批注开头一句话讲清本页是干什么的，独立标"页面说明"不占序号；极端简单页可不写。
3. **一个功能块一条**：按页面区域从上到下编号，一个功能块连贯讲完——不拆块也不塞多条。
4. **颗粒度以「读者会不会追问」为准**：页面看不出来的必须写（操作后发生什么、数据从哪来、钱怎么算、字段限制、什么后台控制、什么三方流转）；一眼能看出的点到为止；易误解点必写（如"提交≠成功，后续还有确认"）。
5. **黑话当场解释**：内部词第一次出现就一句话说清。
6. **数值分两类**：业务定死的直接写值；后台可配置的写明可配置+给当前示例值。只写"由后台配置"或写死可配值都是错。
7. **事实必须准确**：数量、归属、状态以 docs/ 供料为准（执行会话零接触原产物，铁律 3——供料存疑处上报用户裁决，禁钻原产物核对）；演示 mock 数字不进旁批——用户会当真这些规则。
8. **边界与例外要讲**：什么情况不适用、什么由后台控制、什么本期不做。
9. **三方流转用产品语言写**："确认后推送到 X，由 X 派单"——接口名/字段名不出现。
10. **没拍板的规则不写**；内部实现矛盾不向读者暴露。
11. **平实书面语，一种人称贯到底**；长句断开；界面元素可复述作锚点，禁通篇念界面的流水账。
12. **条数以功能块为准**，不硬凑不封顶；纯复述界面没有信息量的句子删。

## 落笔后检查

通篇在念界面吗？黑话解释了吗？数值分清定死/可配了吗（可配的给示例值了吗）？数量归属核对过供料了吗（混 mock 了吗）？人称一致吗？易追问点提前讲了吗？有没有混入没拍板规则、接口名、内部矛盾？

## 交付格式（两种载体同一套文本）

- **静态预览**（rebuilt/preview/）：每页一个隐藏块 `<aside class="anno" hidden>`——首条"页面说明"，其后 `<p class="anno-no">批注一</p><p>正文</p>…`。
- **编辑器版**（第 4 步回装进原产物文件的新风格屏）：同一套文本转成 `data-note` 属性挂在页面元素上（转化脚本自动接线到批注面板；分组按导航结构）。两边文本一字不差，只换容器。
- 旁批不进画布，只进批注面板/容器位。
