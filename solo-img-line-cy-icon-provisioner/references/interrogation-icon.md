# 盘问协议（interrogation-icon）

I0 需求澄清的通用问询能力。**非固定内容**——问题是流式生成的，禁止固定问卷。

## 靶子原则（第一原则）

每个问题必须对着**需求单的某个字段**生成：先看下游（I2 路由）要什么，再问缺什么。填不进需求单任何字段的问题不问。

问题从两处长出来：
- **需求的缺口**——上游说了什么、还缺什么面
- **路由的契约**——供给路由需要什么输入（风格族决定库白名单、交付形态决定供给档位、许可决定能否用某源）

**靶子之上有靶子**：需求本身可能就是偏的——触发协议 1（目的上追）时，靶子暂时从"需求单字段"升级为"这个需求该不该这么做"。

## 七面收敛检查表（收敛标准，非提问脚本）

以下七面是**需求单冻结前的覆盖检查表**——每面 ✓ 才允许冻结。它们不是按序抛出的固定问题；提问顺序与合并方式由对话流动态决定。

| # | 面 | ✓ 标准 | 缺失时的典型问法（供参考，非固定措辞） |
|---|---|---|---|
| 1 | 用途场景 | 什么产物/页面/哪些位置说清 | "用在登录页底部还是整个 App？" |
| 2 | 语义清单 | 逐个列出：每个图标表达什么 | "底部导航 4 个：首页/分类/购物车/我的，对吗？" |
| 3 | 风格族 | 线性/面性/圆角/3D…可判定（有描述或有参考） | "有没有喜欢的 App 参考它的图标感觉？" |
| 4 | 规格 | 显示尺寸 + 颜色方案（currentColor/品牌色） | "导航栏 24px，跟随主题色还是固定品牌蓝？" |
| 5 | 交付形态 | 内联 SVG / base64 / sprite / JSON 子集包；产物约束（单文件 HTML？） | "产物是单文件 HTML 吧？那图标我全部内联" |
| 6 | 许可约束 | 商用/内部演示；接受署名吗 | "对外商用的话我过滤掉需署名的库" |
| 7 | 数量与优先级 | 总数 + 先做核心还是全套 | "先来 5 个核心的，还是一次全套 20 个？" |

**七面不必问全**——上游首轮给齐的面直接 ✓；快速档甚至只需要 3 面（语义/风格/形态）即可冻结。

## 九协议

1. **目的上追（触发式）**：触发条件 = 数量 >10 **或** 范围模糊或上游说不清为什么要（与档位无关；≤10 的简单常规需求豁免）。触发时先向上追问三层——真正希望的结果是什么 → 背后更重要的目标是什么 → 这个做法是不是最好、有没有更直接的打法。避免方向对执行错。结论写进需求单（可能改变数量/形态/甚至改走场景套装路径）
   ```
   例：表面需求"给我 20 个游戏图标"
     ① 真正希望发生的结果？→ "游戏风格卡更有游戏感"
     ② 背后更重要的目标？  → "让人一眼认出这是游戏界面风格"
     ③ 做法是否最好？      → 8 个高频候选+网格对比图让上游挑风格，
        比 20 个直接交付更能达成"风格确认"
   ```
2. **一次一问**：问完等答案，禁止多问轰炸（复合问允许：一句里带两个相关小问）
3. **每问带推荐**：基于语义与行业惯例给建议答案——"游戏场景建议用 game-icons 剪影风（推荐）还是像素风？"（协议 1 的目的三层追问豁免本条——目的层是开放式探询）
4. **人话原则**：永远业务语言。禁止暴露内部术语（前缀/cache/白名单/glob/Iconify API）
5. **能点选不打字**：给选项让上游点；唯一例外是开放性内容（业务描述）
6. **靶子先行**：问之前自查——答案填进需求单哪一面？填不进的不问
7. **换轴自查（收敛前强制卡点）**：感觉快问完了 ≠ 可以冻结。冻结前换视角重查遗漏——**模式 A 向上游显式输出逐条 ✓/✗（轴名翻译成人话，遵守协议 4）；模式 B 豁免展示，自查记录写入需求单冻结稿即可**。不执行此自查 = 没走收敛判定，禁止冻结：
   | 轴 | 自查问题 |
   |---|---|
   | 时间轴 | 上游的工作流里，这批图标的前后环节还有谁（相邻环节的图标漏了没） |
   | 用户轴 | 换位上游视角：拿到交付后第一步做什么——能顺利用起来吗 |
   | 反方向轴 | 如果这是"错误交付"，最可能错在哪（哪些 ✓ 其实是我推的不是他说的） |
   | 对表轴 | 回查七面：每面 ✓ 是真答案还是猜测填充 |
8. **收敛判定**：七面按需求档位覆盖 + 换轴自查全过 + 无未裁决矛盾 = 共识达成，停止盘问。矛盾裁决：以上游最新明确表态为准，仍裁不了回问
9. **确认落盘**：每轮结论即时写回需求单草稿（草稿载体 = 对话内累积的【图标需求单】代码块，冻结时按 demand-sheet.md 模板定稿）；最终冻结需上游明确确认

## 工单自洽性复核

工单是来源方的转述，天然可能丢失页面上下文——描述含糊、条目遗漏、或隐含的形态假设没有说明，都是常态。整理需求单时，除逐项核对语义外，还要**整体审视这批图标的组合合理性**：

- 它们是否属于同一个界面的图标系统？（跨区块来源的图标混在一单里，形态假设往往不成立）
- 单一风格的假设有没有来源方的明确依据，还是我默认的？
- 组合观感与页面类型相称吗？

存疑即问。形态假设错了，生产的每一枚都是错的——问对一次，省掉整批返工。

## 看不见就不该猜：网格对比图前置

风格族拿不准时，**文字问不如给图挑**：

- 同一语义多风格候选 → render_grid.py 出对比图 → "编号 1 线性 / 2 圆角 / 3 剪影 / 4 软3D，要哪种感觉？"
- 这是最高效的澄清——一次视觉交互替代多轮文字拉扯

## 触发时机

- **I0 澄清**：需求模糊/矛盾/缺关键面（主战场）；数量大/范围模糊触发协议 1
- **I3 漏斗**：候选网格图需上游拍板时
- **I5 交付**：上游对交付不满意，需澄清"不满意的点是什么"再定向重找

## 禁止

- **固定问题清单**（问题从缺口与需求单字段动态生成；七面是收敛检查表不是提问顺序）
- 逐个图标问"这个行不行"（该出网格图就出网格图）
- 把中间产物甩给上游（"你看 JSON 里哪个合适"——翻译成人话选项）
- 一次抛多个不相关问题
- 无推荐答案的开放式提问（上游没义务替 AI 思考）
- 对代理调用方闲聊盘问（模式 B 只做字段校验，缺什么列清单要什么）
