# PRD生成器

根据方案书自动生成完整PRD文档，支持开发团队可读、客户可读、AI可理解执行。

## 输入

用户提供方案书文档（来自solo-sale-line-cy-sale-case-gen skill的产物）。

## PRD文档结构

```
PRD文档
├── 1. 产品概述
├── 2. 角色与权限
├── 3. 功能页面清单（索引：页面-功能-角色对应关系）
├── 4. 页面细化 ← 核心章节
│   ├── 4.1 Web端页面
│   └── 4.2 移动端页面
├── 5. 交互流程（用户用例）
├── 6. 接口设计
├── 7. 数据字典
├── 8. 验收标准
├── 9. 非功能需求
└── 10. 开放平台与三方对接 ← 单独成章
```

**结构说明**：
- **第3章 功能页面清单**：索引章节，表格形式展示"页面-功能-角色"对应关系，不重复描述功能细节
- **第4章 页面细化**：核心章节，每个页面详细描述（布局、元素、交互、状态），功能细节只在页面中描述一次
- **第5章 交互流程（用户用例）**：用户视角的操作流程，覆盖主流程、分支流程、异常流程。方案书核心流程需扩展补充，原则：每个角色至少覆盖登录、主操作、数据管理3类用例
- **第6章 接口设计**：API接口说明（不含三方对接，三方对接在第10章）。包含统一规范（鉴权机制、错误码、分页规范、幂等性）
- **第10章 开放平台与三方对接**：第三方系统对接内容，含时序图和数据流向
- 各章节内容按需整合，避免重复

## 生成流程

### 步骤1：解析方案书

从方案书中提取以下内容：

| 方案书章节 | 对应PRD章节 |
|-----------|------------|
| 第2章系统角色 | PRD第2章角色与权限 |
| 第3章客户诉求 | PRD第1章产品概述（需求来源） |
| 第4章终端设计 | PRD第3章功能页面清单、第4章页面细化 |
| 第6章终端功能清单 | PRD第3章功能页面清单（提取功能点） |
| 第7章核心业务流程 | PRD第5章交互流程 |
| 第8章三方开发内容 | PRD第6章接口设计（对接接口） |

### 步骤2：扩展交互流程（用户用例）

从方案书提取核心流程后，需主动扩展补充：

**扩展原则**：
- 每个角色至少覆盖：登录、主操作、数据管理3类用例
- 覆盖主流程、分支流程、异常流程
- 覆盖辅助流程（设置、反馈等）

**扩展来源**：
- 方案书角色诉求 → 提取角色主流程
- 页面细化 → 提取分支/异常流程
- 功能清单 → 补充辅助流程

**输出用户用例模板**：
```
【用户用例：XXX】

角色：[角色名称]
目标：[用户目标]
价值：[业务价值]

步骤：
1. 步骤1：...
2. 步骤2：
   - 条件A → 结果X
   - 条件B → 结果Y

分支：...

异常：
- 异常1 → 处理方式
- 异常2 → 处理方式
```

### 步骤3：校验完整性

交叉对比方案书，确保：
- 每个功能点都有页面承载
- 每个用户用例都有页面支撑
- 每个角色都有功能权限说明

输出对比校验报告：
```
【对比校验报告】
方案书功能点：X个
PRD覆盖功能点：X个 ✓
覆盖率：XX%
缺失项：X项（如有）
```

### 步骤4：生成页面细化

**每个页面的细化模板**（详见references/page-template.md）：

```
## [页面名称]

### 页面概述
- 功能定位：该页面在系统中的作用
- 入口来源：从哪个页面/动作进入
- 出口去向：操作后可能跳转的页面

### 页面区块
| 区块名称 | 作用 | 数据来源 |
|---------|------|---------|
| 区块1 | ... | ... |

### 元素与交互
| 元素 | 操作 | 行为 |
|------|------|------|
| [按钮A] | 点击 | ... |
| [输入框] | 输入 | ... |

### 状态定义
- 默认态：...
- 加载态：...
- 空数据态：...
- 错误态：...

### 完整交互闭环
**主流程**：步骤1 → 步骤2 → 步骤3 → 结束
**分支流程**：
  - 条件A → 路径X
  - 条件B → 路径Y
**异常流程**：
  - 异常1 → 处理方式
  - 异常2 → 处理方式
```

### 步骤5：生成接口设计

为每个跨页面数据交互生成接口说明（不含三方对接）。

**接口设计包含两部分**：
1. 统一规范（必须）
2. 接口详情（每个接口一个表格）

**5.1 统一规范模板**：

```
### X.1 统一规范

#### X.1.1 鉴权机制
- Token放在请求Header：Authorization: Bearer {token}
- Token有效期：X天
- 刷新机制：使用refresh_token换新token

#### X.1.2 统一错误码
| 错误码 | 说明 | 处理方式 |
|-------|------|---------|
| 0 | 成功 | - |
| 1001 | 参数错误 | 提示具体参数 |
| 1002 | 未登录 | 跳转登录页 |
| 1003 | 无权限 | 提示无权限 |
| 2001 | 数据不存在 | 提示数据不存在 |
| 5000 | 服务器错误 | 提示稍后重试 |

#### X.1.3 分页规范
- 默认每页条数：10
- 最大每页条数：100
- 默认排序：按createTime倒序

#### X.1.4 幂等性
- POST请求使用唯一请求ID（X-Request-ID）
- 重复提交返回原结果
```

**5.2 接口详情模板**：

| 接口名称 | 方法 | 路径 | 说明 | 调用方 |
|---------|------|------|------|-------|
| 获取用户信息 | GET | /api/user/{id} | 获取用户信息 | 个人信息页 |

**单个接口详情**：
```
#### 接口名称

**请求**：
```
METHOD /api/path
```

**Header参数**：
| 参数名 | 类型 | 必填 | 说明 |
|-------|------|-----|------|
| Authorization | string | 是 | Bearer {token} |

**Path参数**：
| 参数名 | 类型 | 必填 | 说明 |
|-------|------|-----|------|
| id | string | 是 | 用户ID |

**Query参数**：
| 参数名 | 类型 | 必填 | 说明 |
|-------|------|-----|------|
| page | int | 否 | 页码，默认1 |
| pageSize | int | 否 | 每页条数，默认10 |

**响应**：
```json
{
  "code": 0,
  "data": {}
}
```
```

## 自查检查清单

生成PRD后，必须进行**7轮开发视角自检**。自己发现问题，自己修复，不需要和用户沟通，直到全部通过。

### 自检流程

```
PRD生成完成
    ↓
【自检第1轮】基础完整性检查
    ↓ 发现问题 → 直接修复 → 重新检查
    ↓ 通过
【自检第2轮】开发视角逻辑检查
    ↓ 发现问题 → 直接修复 → 重新检查
    ↓ 通过
【自检第3轮】AI编程友好性检查
    ↓ 发现问题 → 直接修复 → 重新检查
    ↓ 通过
【自检第4轮】接口与页面匹配检查
    ↓ 发现问题 → 直接修复 → 重新检查
    ↓ 通过
【自检第5轮】数据安全与权限检查
    ↓ 发现问题 → 直接修复 → 重新检查
    ↓ 通过
【自检第6轮】边界条件与性能检查
    ↓ 发现问题 → 直接修复 → 重新检查
    ↓ 通过
【自检第7轮】全局总结检查
    ↓ 发现问题 → 直接修复 → 重新检查
    ↓ 通过
    ↓
输出PRD
```

**执行原则**：所有修改我自己处理，不需要和用户确认。

### 自检第1轮：基础完整性检查

**目的**：确保PRD基础结构完整，无遗漏章节

**检查项**：

| 序号 | 检查项 | 检查内容 | 发现问题处理 |
|-----|-------|---------|------------|
| 1.1 | 章节完整性 | 10章是否全部存在 | 缺失则补充章节 |
| 1.2 | 角色完整性 | 所有方案书角色是否都有 | 缺失则补充角色 |
| 1.3 | 页面完整性 | 方案书所有页面是否都有 | 缺失则补充页面 |
| 1.4 | 功能完整性 | 方案书所有功能点是否都有 | 缺失则补充功能 |

**修复原则**：
- 缺失角色 → 根据方案书角色定义补充
- 缺失页面 → 根据方案书页面结构和功能清单补充
- 缺失功能 → 根据方案书功能清单补充

---

### 自检第2轮：开发视角逻辑检查

**目的**：站在开发角度，检查业务逻辑是否闭环、页面跳转是否一致

**检查项**：

| 序号 | 检查项 | 检查内容 | 发现问题处理 |
|-----|-------|---------|------------|
| 2.1 | 页面跳转一致性 | A→B后B能返回A | 不一致则补充返回路径 |
| 2.2 | 数据流转一致性 | 列表和详情数据字段一致 | 不一致则统一字段 |
| 2.3 | 权限一致性 | 角色权限与页面功能匹配 | 不匹配则调整权限 |
| 2.4 | 状态流转一致性 | 状态流转无矛盾 | 有矛盾则修正流程 |
| 2.5 | 角色用例完整性 | 每个角色有3类用例 | 缺失则补充用例 |

**修复原则**：
- 跳转缺失 → 补充完整的跳转路径
- 数据不一致 → 以详情页为准统一
- 权限问题 → 根据角色职责调整
- 用例缺失 → 按"登录-主操作-数据管理"补全

---

### 自检第3轮：AI编程友好性检查

**目的**：确保PRD能被AI正确理解并生成代码

**检查项**：

| 序号 | 检查项 | 检查内容 | 发现问题处理 |
|-----|-------|---------|------------|
| 3.1 | 接口鉴权说明 | 每个接口有鉴权说明 | 缺失则补充鉴权信息 |
| 3.2 | 错误码定义 | 有统一错误码表 | 缺失则补充错误码表 |
| 3.3 | 字段校验规则 | 表单有校验规则和错误提示 | 缺失则补充校验规则 |
| 3.4 | 分页参数说明 | 有默认值和最大值说明 | 缺失则补充说明 |
| 3.5 | 响应数据结构 | 有完整响应JSON示例 | 缺失则补充JSON示例 |
| 3.6 | 页面交互说明 | 按钮行为清晰 | 不清晰则补充说明 |
| 3.7 | 状态定义说明 | 加载/空数据/错误状态都有 | 缺失则补充状态定义 |
| 3.8 | 三方对接时序 | 每个对接有时序图 | 缺失则补充时序图 |

**修复原则**：
- 鉴权缺失 → 按统一规范补充
- 错误码缺失 → 按标准错误码补充
- 校验规则缺失 → 根据字段类型补充合理规则
- 时序图缺失 → 按方案书对接内容补充

---

### 自检第4轮：接口与页面匹配检查

**目的**：确保页面调用的每个接口都已定义

**检查项**：

| 序号 | 检查项 | 检查内容 | 发现问题处理 |
|-----|-------|---------|------------|
| 4.1 | 接口覆盖完整性 | 页面的每个数据请求都有对应接口 | 缺失则补充接口定义 |
| 4.2 | 参数匹配性 | 页面需要的参数接口都能提供 | 不匹配则调整接口参数 |
| 4.3 | 提交接口完整性 | 表单提交有创建/更新接口 | 缺失则补充接口 |
| 4.4 | 删除接口完整性 | 有删除操作的有对应接口 | 缺失则补充接口 |

**修复原则**：
- 接口缺失 → 根据页面需求补充接口定义
- 参数不匹配 → 调整接口参数或页面需求
- 增删改查接口 → 确保每个操作都有对应接口

---

### 自检第5轮：数据安全与权限检查

**目的**：确保敏感数据处理和权限控制到位

**检查项**：

| 序号 | 检查项 | 检查内容 | 发现问题处理 |
|-----|-------|---------|------------|
| 5.1 | 敏感数据加密 | 密码等敏感数据有加密说明 | 明文则补充加密说明 |
| 5.2 | 接口权限校验 | 有接口级别权限校验说明 | 缺失则补充权限校验说明 |
| 5.3 | 越权防护 | 低权限角色无法访问高权限数据 | 有漏洞则补充校验逻辑 |
| 5.4 | 敏感操作日志 | 敏感操作有日志记录说明 | 缺失则补充说明 |

**修复原则**：
- 敏感数据 → 补充加密存储和传输说明
- 权限校验 → 补充接口调用权限校验逻辑
- 越权漏洞 → 补充权限校验机制
- 操作日志 → 补充日志记录要求

---

### 自检第6轮：边界条件与性能检查

**目的**：确保极端情况和性能要求有考虑

**检查项**：

| 序号 | 检查项 | 检查内容 | 发现问题处理 |
|-----|-------|---------|------------|
| 6.1 | 大数据量处理 | 列表接口有分页限制 | 无分页则补充分页说明 |
| 6.2 | 批量操作处理 | 批量删除/导入有处理逻辑 | 无则补充批量处理说明 |
| 6.3 | 极值情况处理 | 列表为空、字符串超长有处理 | 无则补充处理说明 |
| 6.4 | 并发冲突处理 | 同一数据多人同时编辑有机制 | 无则补充冲突处理机制 |

**修复原则**：
- 分页缺失 → 补充大数据量分页说明
- 批量操作 → 补充批量操作处理逻辑
- 极值情况 → 补充空值、超长字符串处理
- 并发冲突 → 补充乐观锁/悲观锁机制说明

---

### 自检第7轮：全局总结检查

**目的**：全局视角审查PRD完整性，交叉检查各章节一致性

**检查项**：

| 序号 | 检查项 | 检查内容 | 发现问题处理 |
|-----|-------|---------|------------|
| 7.1 | 章节交叉验证 | 功能清单与页面细化功能一致 | 不一致则统一 |
| 7.2 | 用例与流程匹配 | 用户用例步骤与交互流程一致 | 不匹配则统一 |
| 7.3 | 接口与数据匹配 | 接口参数与数据字典一致 | 不一致则统一 |
| 7.4 | 术语统一性 | 全局术语表述一致 | 不一致则统一 |
| 7.5 | 文档完整性 | 文档无缺失、无冗余、无矛盾 | 有问题则修正 |
| 7.6 | 可执行性最终确认 | AI能理解并执行开发 | 有疑惑则补充说明 |

**全局检查重点**：
- 第3章功能清单中的每个功能，在第4章有对应页面细化
- 第4章页面的跳转关系形成闭环
- 第5章用户用例的步骤在第4章页面中有体现
- 第6章接口的参数来自第7章数据字典
- 第8章验收标准与前面章节功能对应

**修复原则**：
- 不一致 → 以最详细的那个为准，统一其他章节
- 冗余 → 删除重复内容
- 矛盾 → 分析后保留合理的，修正错误的
- 缺失 → 补充完整

---

### 自检执行流程

直接执行7轮检查，发现问题直接修复，不需要报告格式。

**执行流程**：
```
1. 执行第1轮检查 → 发现问题 → 直接修复 → 重新检查第1轮 → 通过
2. 执行第2轮检查 → 发现问题 → 直接修复 → 重新检查第2轮 → 通过
3. 执行第3轮检查 → 发现问题 → 直接修复 → 重新检查第3轮 → 通过
4. 执行第4轮检查 → 发现问题 → 直接修复 → 重新检查第4轮 → 通过
5. 执行第5轮检查 → 发现问题 → 直接修复 → 重新检查第5轮 → 通过
6. 执行第6轮检查 → 发现问题 → 直接修复 → 重新检查第6轮 → 通过
7. 执行第7轮检查 → 发现问题 → 直接修复 → 重新检查第7轮 → 通过
8. 输出PRD
```

**冲突处理**：
- 每轮修复时，检查是否与前几轮产生冲突
- 发现冲突立即修复
- 继续检查直到全部通过

**执行原则**：
- 直接检查
- 直接修复
- 直接继续
- 不输出报告
- 不需要和用户确认
