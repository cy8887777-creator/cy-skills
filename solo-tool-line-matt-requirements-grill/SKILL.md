# Grill Requirements

This skill is for formal software requirements discovery.

Invoke the installed `solo-tool-line-matt-grilling` skill/capability through the host's normal skill mechanism. If a Skill tool exists, call it with `"solo-tool-line-matt-grilling"`; otherwise read the installed solo-tool-line-matt-grilling/SKILL.md and execute its rules. Do not depend on `solo-prd-line-matt-grill-me` itself.

The bundled solo-tool-line-matt-grilling asks dependency-aware rounds. This wrapper uses 10-question batches when 10 useful questions are currently answerable. Ask fewer when fewer useful questions remain, or upstream answers are required before the next questions become answerable; never guess dependencies or add filler.

Invoke `solo-dev-line-matt-domain-modeling` through the same Skill mechanism only if it is locally available and useful.
`solo-dev-line-matt-domain-modeling` is optional.

Do NOT depend on or require `solo-prd-line-matt-grill-docs`.

# Prototype Factory Integration

When called from `flow-ue-line-xjk-prototype-factory`, read its `references/requirements-discovery.md` before interviewing. All in-scope materials, including collapsed mind-map branches and business resources, must be fully parsed and persisted, then industry research must be completed before the first formal question round. Preserve source IDs and existing FR/BR/OQ IDs. Factory docs are generated delivery views of the resolved requirements model, not independently editable business truth. The same ingestion and confirmation gates apply to micro projects. Do not enter factory stage 2 until critical blockers are resolved and the user explicitly approves the requirement baseline and any remaining non-critical prototype handling.

# Core Principle

Conversation memory is temporary working memory.

Persisted project requirements are the source of truth.

The required workflow is:

Ask the current dependency-safe batch (up to 10 useful questions)
→ user answers
→ interpret all answered items
→ extract requirement facts
→ persist them
→ verify persistence
→ only then ask the next dependency-safe batch

Never accumulate many important answers only in conversation context.

Never wait until the end of a long interview to summarize everything.

# Interview Behavior

Follow the solo-tool-line-matt-grilling style, but use a batch cadence:

1. Ask 10 meaningful questions per interview round when the settled prerequisites allow it. Ask fewer if unresolved prerequisites prevent 10 useful questions, and explain that dependency briefly.
2. Each question must include a concise recommended answer or recommended direction.
3. Keep wording short, concrete and easy to answer.
4. Prefer questions that can be answered by choosing an option, confirming a recommendation, or giving one short clarification.
5. Walk through the design tree branch by branch.
6. Resolve upstream decisions before downstream details.
7. Briefly explain trade-offs only when they materially affect the decision.
8. Challenge vague, contradictory or risky requirements.
9. Do not ask the user questions that can already be answered from supplied project materials.
10. Inspect available Excel, Word, UI designs, prototypes, code and existing documentation first. For large projects, complete and persist all in-scope source ingestion under the `Lanhu Interview Gate` before asking the first interview question.
11. Do not make the user repeat already confirmed information.
12. Distinguish clearly between:
   - USER_CONFIRMED
   - SOURCE_DOCUMENT
   - RECOMMENDED
   - ASSUMED
   - OPEN

A recommendation does not become confirmed until the user accepts it.

Do not ask 10 unrelated questions just to fill a batch. Group each batch around the current module, workflow, conflict set or decision branch.

If fewer than 10 genuinely useful unresolved questions remain in the entire discovery scope, ask only the remaining useful questions. Never create filler questions, repeat resolved questions, or invent ambiguity just to reach 10.

# Requirements Repository Mode

Resolve the repository mode before reading or writing requirement facts. Run
`scripts/init_requirements.py --project-root <absolute-project-root>` and use
the paths it reports for the entire discovery session.

## Governed project mode

Use governed project mode when both `project.config.json` and
`docs/governance/source-of-truth.md` exist. Read the governance file before
continuing. For a project generated by `bootstrap-php-uniapp-project`, use:

| Responsibility | Authoritative path |
|---|---|
| Project identity, delivery targets, directories and project-level status | `project.config.json` |
| Stable feature IDs, phase/scope, lifecycle status and verification evidence | `docs/acceptance/acceptance-baseline.json` |
| Actors, behavior, rules, workflows, exceptions, non-functional requirements and acceptance criteria | `docs/requirements/product.md` |
| Confirmed, rejected, deferred and open decisions plus external dependencies | `docs/requirements/confirmed-decisions.md` |
| Meaningful requirement changes | `docs/requirements/change-log.md` |
| Parsed source observations, Lanhu indexes and conflicts | `docs/requirements/source-analysis/` |

Do not create a top-level `requirements/` directory in governed mode. Do not
create `MASTER_REQUIREMENTS.md` as a second editable product source. Treat the
governed files above as one requirements model with one authority per fact
type. Keep product behavior in `product.md`, decisions in the decision register,
project identity in `project.config.json`, and update the acceptance baseline
atomically when a stable feature ID, scope or lifecycle status changes.

If a host governance document declares different paths, obey it rather than
these bootstrap defaults. Never silently maintain two editable sources for the
same fact.

## Standalone mode

When no governed project markers exist, maintain the existing standalone
repository:

requirements/
├── 00-project-overview.md
├── 01-roles-permissions.md
├── 02-functional-requirements.md
├── 03-business-rules.md
├── 04-workflows.md
├── 05-edge-cases.md
├── 06-decisions-rejected.md
├── 07-open-questions.md
├── 08-change-log.md
├── MASTER_REQUIREMENTS.md
└── source-analysis/
    └── lanhu/
        ├── LANHU_PROJECT_INDEX.md
        ├── LANHU_SCREEN_INDEX.md
        ├── LANHU_FEATURE_SCREEN_MATRIX.md
        ├── LANHU_CONFLICTS.md
        ├── LANHU_INGESTION_PROGRESS.md
        └── modules/

Use these resolved names throughout this skill:

- `<requirements-root>`: the directory containing requirement documents.
- `<canonical-requirements>`: governed `product.md` or standalone
  `MASTER_REQUIREMENTS.md`.
- `<requirements-model>`: the governed authoritative source set above or the
  standalone `MASTER_REQUIREMENTS.md`.
- `<decision-register>`: governed `confirmed-decisions.md` or standalone
  `06-decisions-rejected.md` plus `07-open-questions.md`.
- `<change-log>`: the resolved change-log file.
- `<source-analysis-root>`: the resolved source-analysis directory.

Do not overwrite customer source files.

Original Excel, Word, design files and other source materials should remain read-only unless the user explicitly asks to modify them.

   - deferred requirements

# Context Compact Recovery

Assume context compaction can happen at any time.

If any of the following occurs:

- automatic context compaction
- conversation truncation
- task resume
- new context/session
- uncertainty about previous answers
- uncertainty about a previous decision
- inability to confidently remember the current discovery state

STOP relying on conversational memory.

Before continuing:

1. Re-resolve repository mode from the project files; do not rely on memory.
2. Re-read the relevant files under `<requirements-root>`.
3. Re-read `<decision-register>` and `<canonical-requirements>` if present.
4. Re-read relevant original source materials when needed.
5. Reconstruct:
   - current confirmed facts
   - current scope
   - completed branches
   - unresolved branches
   - current question

Only then continue.

Never treat a compact summary as the authoritative requirements source.

Instead, identify:

## SOURCE_ONLY

Source material contains the requirement and no conflict exists.

## MISSING_REQUIREMENT

Design or system behavior exists but requirement documentation does not describe it.

## MISSING_DESIGN

Requirement exists but corresponding design/interaction is missing.

## CONFLICT

## AMBIGUOUS

Prioritize questions from:

CONFLICT
→ AMBIGUOUS
→ important MISSING_REQUIREMENT
→ important MISSING_DESIGN

# Lanhu MCP Integration

When Lanhu MCP is available, treat it as a source connector, not as a reason to load the entire Lanhu project into conversation context.

The purpose of Lanhu MCP usage is:

Lanhu project
→ enumerate project/page structure
→ ingest by module/batch
→ persist observations immediately
→ build durable screen/feature indexes
→ only then continue to the next batch

Never attempt to fetch, render, inspect, or reason over hundreds of Lanhu pages in one uninterrupted context before persisting the findings.

At runtime, first inspect the actually available Lanhu MCP tools and their schemas.

Do not invent Lanhu MCP tool names, arguments, page identifiers, project identifiers, or URL formats.

Use the exact tools exposed by the current environment.

If the available Lanhu MCP supports project listing, page trees, groups, screen metadata, screenshots, annotations, assets, comments, prototypes, or page details, use the smallest/cheapest metadata operation first and only fetch detailed visual/page content when needed.

# Lanhu Large Project Ingestion Rule

For large Lanhu projects, especially projects containing approximately 100+ screens or many screen states, use incremental ingestion.

Do NOT use this flow:

fetch 500 screens
→ keep everything in context
→ summarize at the end
→ start solo-tool-line-matt-grilling

Use this flow instead:

1. Discover the Lanhu project structure.
2. Build a lightweight page manifest using page names, groups, folders, platforms and stable Lanhu identifiers when available.
3. Group pages into logical business modules or screen families.
4. Select one module/batch.
5. Fetch only the detailed Lanhu information required for that batch.
6. Analyze the batch.
7. Persist all useful facts to disk.
8. Update ingestion progress.
9. Verify persistence.
10. Only then fetch the next batch.

Prefer module boundaries over arbitrary page counts.

When a module is too large, subdivide it into manageable batches. A practical default is roughly 20–40 information-dense screens per batch, but adapt to actual complexity and the capabilities of the current Lanhu MCP.

Never wait for context pressure or compaction before checkpointing.

Every completed module/batch must be recoverable from disk without depending on conversation memory.

# Lanhu + Excel/PDF Cross-Check

When both a functional requirements source and Lanhu designs exist, explicitly identify:

## SOURCE_ONLY

Feature is described by Excel/PDF and the design is consistent.

## DESIGN_ONLY

Lanhu contains a meaningful function or workflow not represented in the requirement source.

## MISSING_DESIGN

Requirement source contains a function but no corresponding design can be found.

## CONFLICT

Lanhu and requirement source disagree materially.

## AMBIGUOUS

The visual design suggests behavior but the actual business rule cannot be safely inferred.

Persist these findings in:

`<source-analysis-root>/lanhu/LANHU_CONFLICTS.md`

Do not automatically turn a visual observation into a confirmed business rule.

For example:

Seeing a “退款” button proves that a refund entry exists in that design state.

It does NOT by itself prove:

- all orders can be refunded
- refund time limit
- full vs partial refund
- approval requirements
- refund calculation
- allowed order states

Those business rules remain OPEN unless another authoritative source resolves them.

# Lanhu Interview Gate

For a large project, formal requirements discovery is prohibited until source ingestion for the current scope is complete. Do not start solo-tool-line-matt-grilling and do not ask the first 10-question round before every gate condition below is satisfied:

1. Every in-scope original source, including PDF, Excel, Word and comparable source materials, has been fully parsed and its useful facts have been persisted to disk.
2. Every discovered Lanhu module in the current scope has completed ingestion and is marked `INGESTED`, or is explicitly marked `EXCLUDED` or `OUT_OF_SCOPE`.
3. `LANHU_SCREEN_INDEX.md` and `LANHU_FEATURE_SCREEN_MATRIX.md` have been updated to reflect all completed in-scope ingestion.
4. Conflicts, missing requirements or designs, and ambiguities have been persisted in `LANHU_CONFLICTS.md` with the appropriate `OPEN`, `CONFLICT`, or `AMBIGUOUS` status.
5. `LANHU_INGESTION_PROGRESS.md` has been updated and verifies that no unprocessed in-scope source or Lanhu module remains.

During source ingestion, persist ordinary business ambiguities, conflicts, and missing rules as `OPEN`, `CONFLICT`, or `AMBIGUOUS`. Do not ask the user about them before the gate opens.

The only question permitted before source ingestion is complete is one whose answer directly blocks continued access to, reading of, or parsing of the remaining source materials. Do not use this exception for ordinary business clarification, prioritization, confirmation, or conflict resolution.

The mandatory sequence is:

complete and persist all in-scope PDF/Excel/Word and comparable source ingestion
→ build the Lanhu project manifest
→ complete incremental ingestion of every in-scope Lanhu module
→ update the screen index and feature-screen mapping
→ persist conflict/missing/ambiguous analysis and final ingestion progress
→ verify every gate condition
→ ONLY THEN start 10-question solo-tool-line-matt-grilling rounds

The solo-tool-line-matt-grilling phase should focus primarily on information that cannot be safely resolved from existing sources.

Priority:

1. CONFLICT
2. AMBIGUOUS
3. high-risk DESIGN_ONLY requirements
4. high-risk MISSING_DESIGN requirements
5. missing business rules
6. permissions/data scope
7. edge cases
8. non-functional requirements

Do not waste user interview turns confirming obvious labels, fields or navigation that Lanhu already proves.

# Question Format

Ask 10 questions per interview round when 10 useful questions are currently answerable; otherwise follow the dependency-aware exception above.

Use a compact numbered format:

1. [问题]
   建议：[推荐方案]

2. [问题]
   建议：[推荐方案]

...

10. [问题]
    建议：[推荐方案]

Language requirements:

- concise and direct
- avoid long background explanations
- avoid repeating source facts the user already knows
- one question should normally fit in 1–2 short sentences
- one recommendation should normally fit in 1 short sentence
- explain the reason only when the trade-off is important; keep it to 1 short sentence
- prefer concrete options over open-ended prompts

Good example:

`1. 退款是否需要平台审核？`
`建议：一期采用平台人工审核，便于控制资金风险。`

Bad example:

Long paragraphs explaining the entire refund domain before asking what the user wants.

Keep all 10 questions focused on the current module or closely related decision set. Do not mix unrelated domains in the same batch unless necessary to resolve a shared dependency.

---

# Periodic Integrity Check

After approximately every 5–10 meaningful decisions, or after completing one major module:

silently check:

- whether all new decisions were persisted
- contradictions
- duplicate requirements
- open questions
- Phase 1 leakage
- requirement ID stability
- rejected requirements accidentally reappearing

Only interrupt the user if a real decision is required.

# Canonical Requirements Model

This is the finalized normalized requirement model.

Use `<requirements-model>` for the active repository mode. In governed mode it
is the coordinated source set declared by the host governance file; in
standalone mode it is `requirements/MASTER_REQUIREMENTS.md`. Never copy a
governed fact into `product.md` merely to create a single physical master file.

Do not continuously rewrite it after every tiny answer during early discovery.

When a major module is complete, or discovery is approaching finalization:

1. re-read all requirements files
2. re-read relevant sources
3. normalize terminology
4. detect contradictions
5. remove accidental duplication
6. preserve OPEN items
7. update every affected authoritative file in `<requirements-model>` atomically

It should contain:

- project overview
- scope
- Phase 1
- actors
- roles
- permissions
- data permissions
- module tree
- functional requirements
- business rules
- workflows
- state transitions
- exceptions
- integrations
- non-functional requirements
- acceptance criteria
- rejected/out-of-scope features
- open questions
- stable requirement IDs

`<requirements-model>` is the authoritative input for final deliverables. Each
fact type still has exactly one editable source.

# Finalization Gate

Before declaring discovery complete, audit:

## Scope
Is Phase 1 clearly separated from later phases?

## Functions
Are major functions sufficiently detailed?

## Roles
Is every important action associated with an actor?

## Data permissions
Is it clear which data each role can access?

## Business rules
Are important calculations and restrictions documented?

## States
Are important stateful entities complete?

## Exceptions
Are major failure cases covered?

## Conflicts
Are source conflicts resolved or marked OPEN?

## Rejected items
Have rejected features stayed rejected?

## Acceptance
Can important requirements be verified?

If unresolved non-critical items remain, they may stay OPEN.

Do not block delivery unnecessarily.

# Final Deliverables

When the user asks for final deliverables:

DO NOT generate them primarily from conversational memory.

Required pipeline:

`<requirements-model>`
→ consistency audit
→ Excel
+ PRD

Excel and PRD must use the SAME requirement model.

Do not independently invent content for each deliverable.

# Excel / PRD Consistency Check

Before final delivery verify:

- every Phase 1 functional requirement exists in Excel
- every major Phase 1 requirement is described in PRD
- requirement IDs match
- terminology matches
- permissions match
- business rules match
- scope phase matches
- rejected items do not return
- OPEN items remain visibly OPEN

If inconsistency exists:

fix the requirement source first,
then regenerate the affected output.

Do not patch two inconsistent documents independently.

# No Hallucination

Never invent material requirements such as:

- settlement rates
- commission
- payment providers
- refund rules
- role permissions
- approval rules
- field requirements
- timeouts
- Phase 1 scope
- pricing calculations
- state transitions

If unknown:

OPEN

If suggested:

RECOMMENDED

If accepted:

CONFIRMED

# Non-Negotiable Rules

1. Ask 10 meaningful questions per interview round, unless fewer useful questions remain or unresolved prerequisites prevent 10 currently answerable questions.
2. Every question must include a concise recommendation.
3. Keep questions and recommendations short, clear and easy to answer.
4. Use `solo-tool-line-matt-grilling` for depth and dependency-aware design-tree reasoning; apply this wrapper's concise 10-question batch cadence only to currently answerable questions.
5. Read existing project materials before asking redundant questions.
6. Persist all meaningful answers BEFORE asking the next batch.
7. Conversation memory is not the source of truth.
8. Preserve rejected decisions.
9. Preserve open questions.
10. Use stable requirement IDs.
11. After context compaction, re-read persisted requirements.
12. Before final delivery, re-read all requirements.
13. Use the resolved `<requirements-model>` as final-deliverable input; never create a parallel master or duplicate a governed fact into another editable file.
14. Excel and PRD must originate from the same source.
15. Never let Phase 2 silently enter Phase 1.
16. Never let rejected features silently reappear.
17. Never use compacted conversational memory to override persisted confirmed requirements.
18. Prefer evidence from original files over guesses.
19. The purpose is not just to interview the user; it is to build a durable software requirements knowledge base.
20. When Lanhu MCP is available, never load a large project into context before persistence; ingest incrementally by module/batch.
21. After each Lanhu batch, persist observations and update LANHU_INGESTION_PROGRESS before fetching the next batch.
22. Keep stable Lanhu source identifiers so exact pages can be re-opened later instead of relying on visual memory.
23. Treat Lanhu visuals as source evidence, not automatically as confirmed business rules.
24. After compaction, resume from persisted Lanhu indexes/progress instead of re-reading the entire project.
25. For large projects, never start formal requirements discovery or the first 10-question round until every in-scope PDF, Excel, Word and comparable original source has been fully parsed and persisted; every discovered Lanhu module is marked `INGESTED`, `EXCLUDED`, or `OUT_OF_SCOPE`; and the screen index, feature-screen mapping, conflict/missing/ambiguity records, and ingestion progress are fully updated.
26. During source ingestion, record ordinary business ambiguities, conflicts, and missing rules as `OPEN`, `CONFLICT`, or `AMBIGUOUS`; do not ask the user about them before ingestion is complete.
27. Before ingestion is complete, ask a question only when its answer directly blocks continued access to, reading of, or parsing of the remaining source materials.
