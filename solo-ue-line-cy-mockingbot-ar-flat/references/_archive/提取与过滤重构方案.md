> 背景：连续多轮排查「丢元素」问题，最终定位根因不在翻译/过滤/排版，而在**提取阶段本身漏读**。

## 一、问题总结（已用 CDP 探针实证）

### P1 · 提取 walk 范围太窄（主因）
- `extract_en.mjs` 仅从选中画板 `vp = .group-list .tree-node.rResCanvas` 的 `.children` 开始递归 `walk()`。
- 墨刀 SPA 把部分 UI 元素（尤其某些交互指示层）渲染到了画板 DOM **之外**（全局 overlay / portal 层）。这些元素视觉上落在画布区域内，但不在 `rResCanvas` 子树里。
- **探针实测（Ludo 对战首页）**：
  - 全文档：`InteractionMarker` 26 个、`#298DF8` 蓝闪 SVG 28 个
  - 画板内：仅 19 个 / 19 个 → **差 7 个 Marker + 9 个蓝闪在画板外**
  - 画板实际可见节点 543 个，旧提取只拿到 357 个 → **约 186 个节点丢失**

### P2 · 画板选取逻辑 ~~待确认~~ → **已解答（2026-09-01 18:25 实测）**

> PM 追问「复刻的是英文页还是中文页，为什么有英文有中文」→ CDP 探针实测澄清。

**结论：复刻的是英文画板；3 个中文按钮是墨刀原稿漏翻，非提取/渲染错误。**

同一页面 DOM 同时挂着 **3 个 375×812 画板候选**：

| 候选 | CJK | 叶子文本 | 中文内容 |
|---|---|---|---|
| **A（当前选中）** | **12** | 27 | 仅 `快速开始` `开启对战` `创建房间` |
| B | 53 | 27 | `任务` `签到` `排行` `通行证` `宝箱` `幸运转盘` `战队战争` `锦标赛` `主活动` `[Main Event]7月ludo活动即将结束…` + 上述 3 条 |
| C | 12 | 27 | 同 A（另一渲染态，屏幕宽 549px） |

- **A / C = 英文画板**（UI 主体全英文：Quests / Check-in / Rankings / Battle Pass / Chest / Lucky Wheel / Tournament / Main Event / Crew War）
- **B = 中文画板**（UI 主体全中文）
- **关键佐证**：连中文画板 B 里，`快速开始` / `开启对战` / `创建房间` 这 3 个按钮**同样是中文** → 说明设计稿作者在这张英文 UI 上**漏翻了这 3 个按钮**，属源稿问题。

**对原疑问的回答**：
- 「是否真无纯英文画板」→ **有英文画板，但非 100% 纯英文**，`CJK=12` 即这 3×4=12 个汉字。
- 排序选 CJK 最少（A/C 的 12 < B 的 53）**结果正确**，但依赖排序仍脆弱 → 维持方案 C 的**关键词锁 + URL 参数定位**。

**对阿语翻译的影响（PM 已拍板 2026-09-01 18:29）**：

> 「可能是原型版本的问题，那里忘翻译了。反正以后读取、翻译都是找英文页面，如果英文页面真的有部分文字忘翻译，还是中文，那就**中文直接翻阿语**，回头我会给你一个**术语对照表**。」

即定为：
1. **读取、翻译一律以英文页面为源**（不采用"回填英文再翻"方案）。
2. 英文板里漏翻的中文 → **直接 中文 → 阿语**，不做 EN 中转。
3. **PM 将提供术语对照表**，表内词条优先级高于任何自动/模型翻译，且应跨页跨项目复用。
4. 这是原型版本问题（设计师漏翻），不是提取/渲染缺陷 → **不需改代码**，只需在翻译表补 CN→AR 词条。

已同步写入 `spec.md`：§1.2（画板选取硬规则 + 修正旧文档"CJK=0"的错误表述）、§9 坑8（改写为"英文板也含漏翻中文"）、§10.1（新增「语言源优先级」小节）。

### P3 · 过滤位置错误（提取阶段就丢节点）
- `extract_en.mjs` L142 入队门槛：
  ```js
  if (visible && (rec.text || rec.src || rec.st || rec.svg)) nodes.push(rec);
  ```
- 一个节点必须「有文本 / 有 src / 有非空样式 / 有 svg」才被收录。
- **纯定位容器**（透明背景、无边框、无 transform、无文本、无 svg）→ `st={}` → `rec.st` 为 falsy → **整节点被丢弃**。
- 这与 PM 诉求冲突：那些"空 div / 矩形"正是后续组合效果的基础元素，必须保留。

## 二、PM 需求记录（过滤逻辑重写 · Q2）

> 以下为 PM 明确指令，原文转述：

1. **过滤时机：放在翻译之后（布局调整后）**
   - 提取阶段**不做任何业务过滤**（仅排除页面外参考元素）。
   - 过滤应在 `gen` 阶段、且**必须晚于翻译 + RTL 布局调整**之后执行。

2. **过滤范围：只过滤交互覆盖层，两类**
   - 橙色热区块（墨刀交互热区：半透明橙 `rgba(255,140,25,0.15)` + 橙描边）
   - 蓝色小闪电（`#298DF8` 亮蓝 SVG 图标 / `InteractionMarker` 类元素）
   - **除此之外一律保留**。

3. **基础元素必须保留**
   - 空的 div、矩形元素（rect）、无文本的容器等——即使没有内容、没有可见样式——**也要原样保留**。
   - 原因：我们会用这些"无内容的基础元素"来组合做视觉效果（阴影/边框/圆角/定位锚点等）。

4. **过滤规范必须做严谨**
   - 过滤判定要可解释、可审计，避免误伤真实 UI。
   - 橙块匹配要精确（仅 `rgba(255,140,25,0.15)` 半透明橙签名，不能误删实心橙色品牌按钮）。

## 三、重构方案（待测试）

### A. 提取阶段：扩大 walk 范围 + 取消属性过滤

**改动 1 · walk 起点扩大 + 坐标裁剪**
- 不再 `walk(vp.children)`，改为从 `document.body`（或 `.group-list`）开始遍历。
- 用画板自身 `boardRect = vp.getBoundingClientRect()` 做**坐标裁剪**：只收录「视觉中心落在画板矩形内」的可见元素。
- 这样画板外的 overlay（但视觉落在画布上）也能被收录。

**改动 2 · 取消 L142 属性门槛**
```js
// 旧：
if (visible && (rec.text || rec.src || rec.st || rec.svg)) nodes.push(rec);
// 新：全量捕获（仅按坐标裁剪 + 可见性）
if (visible && inBoardRect(r, boardRect)) nodes.push(rec);
```
- 每个节点无论有无文本/样式，只要可见且在画板内 → 收录。
- `st` 即使为空也保留基础几何（x/y/w/h 一定记）。

**改动 3 · 画板选取增强（对应 P2）**
- 若候选画板 CJK 均 > 0，记录告警（不擅自选），交给 PM 判断是否需补英文源。
- 候选画板数 > 1 时，在输出里列出全部候选 cid/CJK/文本数，便于核对。

### B. 生成阶段：过滤后移 + 收窄到两类

- 当前 `gen_ar_flat.mjs` 已是 hide-mode（交互层 `opacity:0` 不整删），且对**所有节点**都发射 div（基础元素本就保留）→ 与 PM 需求一致。
- 需确认：gen 的 hide 判定**只认两类**（橙块 + 蓝闪），不波及任何基础元素。
- 过滤执行点：确保发生在「翻译 + RTL 镜像 + 布局调整」全部完成后（当前 renderNodes 里 hide 判定在样式构建后、类型分支前，位置正确）。

### C. 方案 A vs B（walk 扩大方式）

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| A. 坐标裁剪（推荐） | body 起 walk + boardRect 坐标过滤 | 一次拿全，含画板外 overlay | 需严格坐标裁剪防侧边栏渗漏 |
| B. 双源合并 | 主 walk 不变 + 额外扫 InteractionMark/蓝闪补入 | 改动小、风险低 | 只补全交互层，不解决其他画板外元素 |

**倾向 A**：PM 要求保留所有基础元素，A 能最完整捕获；B 只补交互层，无法解决"画板外但非交互"的遗漏。

## 四、Q1 回答：4 个 html 模式会影响读取吗

**结论：会影响，但当前用法正确。**

证据（直接对比 4 个 html 文件，除一行外完全相同）：

| 文件 | `HZv5_PREVIEW_MODE` | 渲染模式 |
|---|---|---|
| `index.html` | `"device"` | 设备预览（正常用户视角）✅ |
| `演示模式.html` | `"device"` | **与 index 完全相同** |
| `标注模式.html` | `"inspect"` | 检视/标注模式（会加标注 UI/overlay）⚠️ |
| `总览模式.html` | `"read_only"` | 只读/总览模式（可能改布局/禁用交互）⚠️ |

- `index.html` 与 `演示模式.html` 等价，都是 `device` 正常预览 → 我们要的就是这个。
- `标注模式`(inspect) 会注入标注/检视相关 DOM，污染提取。
- `总览模式`(read_only) 可能以网格展示全部页面或改变渲染，破坏 `.group-list .tree-node.rResCanvas` 选取逻辑。
- **规则**：提取脚本必须始终打开 `index.html`（或 `演示模式.html`），**绝不**用 `标注/总览` 模式。当前 `extract_en.mjs` 的 Chrome 启动命令喂的就是 `index.html` → 符合。建议在 skill 文档显式写明此约束。

### P4 · 缩放根因（重构测试第一步实测新发现 · 比 P1 更底层）

> 对 Ludo Battle Home 做「全量读取 + 原样复刻」测试（`test_read_ludo.mjs`）后，发现此前 P1「walk 范围太窄」只是表象，**真正的根因是缩放**。

- **现象**：headless Chrome 视口过小（实测 `innerWidth×innerHeight = 764×429`），墨刀预览按"fit-to-window"把 375×812 画板缩到约 **41.4×89.7**（scale≈0.11）。
- **后果**：`getBoundingClientRect()` 拿到的是**缩放后坐标**，导致：
  1. 所有节点坐标被压扁到 41×90 空间 → 复刻内容全挤在顶部，底部（y≈770）刚好越过 90px 边界被裁掉 → **底部 5-Tab 导航整段丢失**（正是 PM 最初截图的痛点）。
  2. 旧脚本在同视口下反而"碰巧"出过全页，是因为当时视口大（scale≈1）把坐标读对了——属偶然，不可靠。
- **验证**（CDP 几何探针 `diag_geo.mjs`）：
  - 画板 `offsetWidth/Height = 375/812`，但 `getBoundingClientRect = 41.4×89.7` → scale = 9.056（X/Y 一致，均匀缩放）。
  - 即使调用 `Emulation.setDeviceMetricsOverride({1400,1000})` 也**未能**让墨刀放大画板（仍 41.4×89.7），故不能依赖放大视口。
- **修复（已在测试脚本落地，验证有效）**：
  1. **反缩放**：对每节点用 `scale = offsetWidth / getBoundingClientRect().width` 把屏幕坐标×scale 还原为设计坐标（375×812 空间）。scale 均匀，单因子即可。
  2. **编辑器外壳剔除**：body 起 walk + 画板坐标裁剪后，仍有 28 个墨刀 SPA 外壳容器（`main-content`/`mb-viewport`/`preview-content-container`/`fixed_area` 等）因 bounding box 达 12000×9000 仅擦过画板被误收。用尺寸阈值 `w > boardW*3.2 (≈1200) || h > boardH*3.2 (≈2598)` 剔除，**仅跳过节点本身、仍递归其子节点**，确保页面内容不丢。
  3. **设计空间裁剪**：坐标还原后，以设计画板 `[0,375]×[0,812]` 做最终裁剪，保证只收手机屏内元素。
- **实测结果（Ludo Battle Home 单页）**：
  - 节点数 **376**（旧 357；含 5-Tab 底部导航、状态栏图标、57 个 SVG、29 文本、307 空容器）。
  - 节点按 y 带分布 0–800 连续覆盖（71/35/51/68/47/11/37/43），**底部导航 5 个 `canClickableHighWidget` 已完整捕获**（x=26/84.6/153.2/221.8/290.4，各 68.6×56）。
  - 复刻文件：`导出-ludo测试/ludo_readtest.html`（平铺、不翻译/不过滤/不镜像，供直观看读取质量）。

## 八、P6 · 方案 C：嵌套渲染（PM 拍板采纳，当前最佳效果 · 2026-09-01）

> PM 结论：**「可以了，现在是最好的效果，先记录到 md 里，一会一起调整」**
> 即：本方案为**当前基线**，暂不改 skill 脚本，等 PM 统一给出调整指令后一并实施。

### 8.1 为什么必须嵌套（展平方案的死穴）

P4 修复后提取已正确（scale 1.478 → 427 节点，尺寸真实），但 V2 复刻仍出错。根因在**生成层的层叠上下文被展平破坏**：

- 所有节点被渲染为**同一层绝对定位的兄弟 div**。
- 后果：某个父容器的背景，作为"兄弟"渲染时，**会盖在它自己的子节点之上**。
- 实测试错（V2 复刻截图）：
  | 缺陷 | 根因 |
  |---|---|
  | 「Ludo」标题被大白块盖住 | 父容器白色背景作为兄弟节点，层序在其子文字之后 |
  | 底部 5-Tab 图标不可见（只剩一条蓝色进度条） | Tab 图标 SVG 被其父/祖容器的背景兄弟节点遮住 |
  | 右侧 Rankings / Battle Pass 任务卡被半裁 | 外层卡片背景兄弟节点盖住并裁切 |

**结论：DOM 树结构本身就是层叠信息，展平即丢失。**

### 8.2 方案要点（5 条）

1. **保留 DOM 树**：walk 时为每个节点记录 `parent` 索引 + `depth`，渲染时按树递归嵌套，不再展平。
2. **子节点相对父级定位**：`rx = n.x − parent.x`、`ry = n.y − parent.y`；父级 `position:absolute` 自动成为子级的 containing block。
3. **还原 z-index**：捕获 `getComputedStyle().zIndex`（非 `auto` 时输出），修复同层内前后关系。
4. **还原父级 overflow 裁剪**：捕获 `overflow`（非 `visible` 时输出到父节点），让父容器对子内容做真实裁剪/滚动裁切。
5. **隐藏子树整棵跳过**：`display:none` / `visibility:hidden` / `opacity ≤ 0.01` 的节点，其**整棵子树**不再递归（避免不可见节点污染结构）。
6. **SVG 内部不深入**：`tag === 'svg'` 时直接收口，其内 `path/g/defs` 等不再当作独立画板元素。

## 九、Q2 澄清：过滤发生在哪一步

> PM 疑问：「什么意思，是读取时是否要过滤吗？」

**不是。过滤不在读取（extract）阶段，而在生成（gen）阶段的最末端。**

PM 自己定的规则（本文档第二节 Q2 原文）：

> 1. **过滤时机：放在翻译之后（布局调整后）** —— 提取阶段**不做任何业务过滤**（仅排除页面外参考元素）。

所以完整管线是：

```
① 提取 extract   →  全量读取，零业务过滤（橙热区、蓝闪照收）
② 翻译 translate →  英文 → 阿语
③ 布局调整       →  RTL 镜像 / 宽度自适应 / 文本换行
④ 过滤 filter    →  ★ 只在这里做，且只滤两类：
                       · 橙色热区块 rgba(255,140,25,0.15)
                       · 蓝色小闪电 #298DF8 / InteractionMarker
⑤ 输出 HTML
```

**为什么必须后移**：
- 提取阶段过滤 → 元素没了，后续翻译 / RTL 镜像 / 布局调整全部失去参照物，位置算不准。
- 先翻译 + 布局调整 → 元素在阿语 RTL 下的最终位置已确定，此时再隐藏交互指示层，不会牵动任何布局。

**所以第 2 条待办的真实含义**：
> 「是否在技能里落地 Q2 后置过滤规则」——即确认橙块 + 蓝闪的**精确识别签名**与**隐藏方式**（当前 skill 已是 `opacity:0` 安全隐藏模式，不整删），**与读取无关，读取继续全量照收**。
