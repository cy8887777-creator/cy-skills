> 本文解释本技能背后的问题、目标与对策，是其余所有规范的“为什么”。

## 1. 问题：AI 做设计为什么会均值化

### 1.1 下一个词元预测 + 偏好训练 = 委员会式设计 ◆

大语言模型是“下一个词元预测器”：每一步都根据海量样本预测最可能出现的下一个词元；输出再由人类打分并回灌训练，模型由此学会做**一致、安全、符合大多数人偏好**的选择。

这让模型擅长大多数任务，却天然不擅长设计。生成设计时，模型逐词元构建页面，每遇到一个设计决策（用什么颜色、元素怎么排），都会填入“最可能讨好所有人”的选项。结果是重复而平淡的设计——**终极版的委员会式设计（design-by-committee）**。

### 1.2 “听起来随机”不等于“真的随机” ◆

只要求“独一无二、每个决定都完全随机”，输出确实会变，但依然缺乏多样性：同样的配色、同样的结构，甚至同样牵强的隐喻（例如反复出现的“陶艺”比喻）。模型在预测*听起来*随机的词元，而不是*真的*随机。

> 典型的默认产物：紫色系渐变、左文右图、顶部导航、CTA 在标题下方——“看起来像所有 AI 设计的网站”。

### 1.3 四种偏好叠加，进一步拉向均值

| 偏好 | 表现 | 后果 | 来源 |
| --- | --- | --- | --- |
| 代码偏好 | 爱写代码，少用图像工具 | 用渐变、形状、基础图案充当视觉 | ◆ |
| 加法偏好 | 爱加不爱减 | 过度解释、无用元素堆积 | ◆ |
| 自评偏差 | 审视自己的代码、决策与理由 | 无法“退一步看全局”，难以“think different” | ◆ |
| 安全偏好 | 回避风险 | 不敢删减、不敢打破规则 | ◆ |

## 2. 目标：什么是好设计

### 2.1 原文的定义 ◆

好的设计**从感受出发，追求情绪反应**；它会打破规则，用令人难忘、出人意料的选择取悦用户。这恰恰与模型的天性相反——模型在每一步都做最可预测的选择。

同时，好设计必须**服务于实际用途**：AI 能做出惊艳的视觉，但设计是否合理、是否流畅、是否真正服务用户，要靠人的判断。

### 2.2 品味的可操作定义 ◇

“品味”难以直接要求，但可以拆解为四个可检验的维度：

| 维度 | 含义 | 检验问题 |
| --- | --- | --- |
| 主张 Point of view | 有明确的立场与情绪目标 | 能否用一句话说出“它想让人感受到什么”？ |
| 一致 Coherence | 所有决定服务于同一主张 | 去掉某个元素，主张会变弱还是更清晰？ |
| 克制 Restraint | 敢于留白、敢于删除 | 屏幕上每个元素都能说出作用吗？ |
| 工艺 Craft | 细节经得起放大 | 间距、对齐、字号、动效是否都有规则可循？ |

## 3. 对策：五条公理与问题的对应

| 问题 | 公理 | 关键手段 | 阶段 |
| --- | --- | --- | --- |
| 模型无法随机 | 随机性来自外部 | 种子字符串（String Seed of Thought） | 发现 |
| 点子趋同 | 品味来自人 | 野心简报、灵感阶梯中的品味批注 | 发现 |
| 自评偏差 | 制作与评判分离 | 只看截图的独立评审回路 | 定义 |
| 代码偏好 | 视觉要有真实素材 | 图像 / 视频生成、抠像、关键帧过渡 | 定义 |
| 加法偏好 | 成品靠减法 | 减法流程、AI 痕迹检查表 | 交付 |

## 4. 流程：为 AI 代理改造的双钻模型

原文松散借鉴了双钻设计流程（Double Diamond），把面向人类设计师的流程改造为面向 AI 代理团队的三个阶段：◆

```
   发现 Discover          定义 Define            交付 Deliver
   ◇ 发散                 ◆ 收敛为个性            ▪ 打磨
   多方向、大胆、冒险      评审回路 + 素材         减法 + 聚焦 + 验收
   ─────────────▶        ─────────────▶         ─────────────▶
   产出：方向 + 简报       产出：定型设计           产出：可上线成品
```

- **发现**：在空白画布前先广后深，用外部随机性与大胆简报探索多种方向；
- **定义**：把模型推出熟悉的模式，串联多个模型，让设计获得独立身份；
- **交付**：打磨掉粗糙边角，聚焦关键元素，得到惊艳且可用的成品。

> 经典双钻为 发现 / 定义 / 开发 / 交付 四段；本技能把“开发”并入“定义”，因为 AI 代理的实现速度让“边做边定”成为可能。◇

## 5. 角色分工

| 角色 | 由谁担任 | 职责 | 不做什么 |
| --- | --- | --- | --- |
| **品味总监** | 人（用户） | 选择方向、注入品味批注、推动减法、做最终取舍 | 不做像素级实现 |
| **协调者** | **主会话 Claude Code** | 走激活协议、阶段切换、AskUserQuestion、用户参与节点判定 | 不写代码（除非当实现者） |
| **实现者** | **主会话 Claude Code**（**不派子代理**——直接 Write/Edit/Bash 写代码） | 写代码（HTML / JSX / Vue / 任何前端栈）→ **产物是代码资产**，可工程化 / 可导入 Figma 二次编辑；调当前环境可用的生图能力生成图片/视频；按评审意见修改 | 不判断”是否够好” |
| **评审者** | **`Agent` 派 `general-purpose` 子代理**（大模型，独立上下文） | 只看截图，给出美学意图、差距、评分 | 不看代码、不知道阈值、不知道历史 |
| 素材工坊 | 当前环境可用的生图能力（探查式） | 实现者调用，生成图像、循环片段、关键帧过渡 | 不决定版式 |

原文的经验来自管理人类设计团队：早期，团队对“界面应该如何工作”的先入之见限制了创造力，总回到同样的老点子；通过严谨的流程，团队学会停止重造舒适区，转而从可能性的边缘寻找新东西，并把细节打磨到 Apple 级别。如今 AI 代理能在数小时内完成过去需要数周的工作——前提是给它正确的引导。◆

## 6. 成本模型 ◆

评审只做“高管决策”，因此可以用大而贵的模型，而不会失控：原文案例中，评审模型的输出 token 占比**不到 10%**；若直接让大模型重做设计，成本约为两倍，耗时也更长。

> 经验法则：便宜快速的模型干活，强模型提供品味。但实现模型不能太小——它仍需有能力把设计方向执行到位。

## 7. 边界与伦理 ◇

- **原创性**：参考图是情绪板与质量基准，不是临摹对象；禁止照抄他人作品。
- **素材合规**：确认生成素材的使用条款；避免生成可识别的真实人物、商标与受版权保护的角色。
- **可用性优先**：风格探索不得突破可访问性底线（对比度、键盘、焦点、减少动效）。
- **模型会进步**：今天行不通的提示，明天的新模型可能做得到——保存失败提示并定期重测。
- **透明**：在设计记录中注明哪些素材由模型生成、使用了哪个模型。

## 8. 为什么这样设计（本技能的工作机制）

### 8.1 四层执行架构

| 层 | 承担什么 | 为什么不能用别的层替代 |
|---|---|---|
| **外部脚本层** | 种子生成（`scripts/seed.mjs`） | 模型只能预测"听起来随机"的词元；真实随机性必须来自系统熵 / 加密源 |
| **提示词模板层** | 12 个提示词（`references/prompt-library.md` P1-P12） | 把"评审该怎么评""减法该怎么减"这些主观判断**提前固化为字面提示**，避免每次重新表达 |
| **子代理评审层** | 视觉评审（`templates/judge-prompt.md`） | 写码代理审视自己的代码有确认偏误；评审必须独立上下文、只看截图 |
| **用户协作层** | 5 项激活 + 简报确认 + 减法决策 | 品味来自人；关键节点必须人参与 |

### 8.2 三阶段与五公理的对位

| 阶段 | 对应公理 | 关键工具 |
|---|---|---|
| 发现 | 随机性来自外部 + 品味来自人 | seed.mjs + discover.md 4 技法 |
| 定义 | 制作与评判分离 + 视觉要有真实素材 | 实现者（写代码）+ 评审者（judge-prompt.md） + media.md |
| 交付 | 成品靠减法 | ai-tells-checklist.md + deliver.md |

任何一公理失守，对应阶段就滑回均值。

### 8.3 关键设计选择（为什么这么做）

- **种子字符串而非提示词要求随机** —— Sakana AI 论文证明：让 AI 自己"随机"，结果仍然趋同；外部注入的随机串才能产生真正不同的方向。
- **评审独立 Agent 而非主会话自评** —— 写码代理看自己代码有确认偏误（实证：8 轮自评中 6 轮穿帮）；独立上下文 + 零沉没成本。
- **提示词冻结（P6 不变）** —— 阈值写进提示会"污染"评审（评审会按提示要求给分）；冻结才能让评分客观可比。
- **"PASS 含金量原则"总纲** —— 模型对脚本的 PASS 是契约；检测器拿不准必须 REVIEW，不能"差不多就行"。

## 9. 事故驱动的加固点（为什么有这些规则）

本技能的每条规则背后都对应一类已被验证过的失败模式：

| 规则 | 防的事故 |
|---|---|
| 必须用脚本生成种子 | 4 个 Claude Code 实例用同一提示得到 4 份几乎一样的"紫色渐变"——模型想象不出真正的随机 |
| 评审独立上下文 | 写码代理看自己代码给 8.5 分，独立评审给 6.2——确认偏误约 2.3 分 |
| 停止阈值不写进提示 | 阈值写进 P6 后，评审分数被锚定到阈值附近，评分不再客观 |
| 减法 + 1 屏 1 主角 | AI 倾向"过度解释"，用户要求"极简"初版仍拥挤——必须显式列出删除类别 |
| 5 项激活协议 | 用户说"随便"会让代理抢跑，导致方向完全错——必须强制 5 项 |
| 用户"停" = 冻结 | 历史事故：用户选"就此停下"后模型仍继续修完——违抗明确指令 |
| 种子不外显 | 种子字符出现在设计中 = 失败（用户能看到随机串 = 穿帮） |
| 评审 > 3 轮设上限 | 无上限会"为讨好评审"耗 token，停滞也不报告 |
| 简报需用户确认 | 不确认就进入实现 = 整轮返工，浪费种子 + 方向探索 |

每条规则都是"已经翻过车才立的规矩"。新增规则时也走这个标准：先有事故，再有规则。

## 10. 已知边界与未覆盖场景

### 10.1 本技能不实现

- **自动图像/视频生成** —— P8/P9/P10 引用图像生成但本技能**不直接调 API**；应调用用户已有的图片生成 skill。详见 `references/start-guide.md` 工具节。
- **跨文化审美的种子规则** —— `scripts/seed.mjs` 默认基于 A-Z / a-z / 0-9 字母表；其他字符集（中文/日文/阿拉伯文）需扩展 alphabet。
- **自动减法** —— 减法决策由用户在交付阶段拍板（不能模型自决"删什么"）。

### 10.2 与其他 skill 的协作

- **生图/视频能力（探查式）**：实现者写代码时探查当前环境可用的生图能力（T2I + I2I + T2V）——有则用它（例：本机装了 solo-img-line-cy-bailian-image-gen/bailian，qwen-image-3.0-pro / wan2.7-image-pro / wan3.0-video 已验证可用）；无则降级外链图库/占位并告知。本技能 P8/P9/P10 需要它。
- **flow-front-ui-line-cy-img-to-code**（单图生成前端代码技能）：**独立 skill**，**不是本技能下游**——它是"截图 → HTML"的高保真还原，与本技能的"代码即设计"是平行方向。
- **flow-front-ui-line-cy-design-pack-pipeline**（多图管线技能）：**独立 skill**——多页项目级管线，与本技能各自解决不同问题。
- **Pipeline 1（0 → 高保真美观的交互效果图，**待建**）**：从 0 做一整套软件的高保真 HTML 效果图（多页 HTML + CSS + 资产），调本技能生成"主要页面"，次要页面 Pipeline 自己补
- **Pipeline 2（lo-fi 交互原型 → hi-fi 交互原型，**待建**）**：用户已有 lo-fi HTML，调本技能做"重设计"，升级为有品味的高保真交互原型

### 10.3 诚实声明

- 种子解读**不能保证每次都产生优秀方向**——90% 来自模型对子模式的联想，主观性大；用户参与"品味批注"是品味注入的关键步骤。
- 评审分数**有 ±0.4 左右的方差**——单次评分波动大；高方差任务建议取 3 次中位数（`references/define.md` §9）。
- "像不像工作室水准"是**人眼判断**——评审只是辅助；最终交付建议用户本人过目。
