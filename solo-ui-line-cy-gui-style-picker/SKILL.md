# solo-ui-line-cy-gui-style-picker —— 风格选型比稿

把"这个项目用什么风格"从口头讨论变成**看得见的比稿决策**。产出=用户选中的确定值（写入 `intake/selection-result.json`），主流程据此升 start-doc 1.0。

> 总纲：**设计的第一性是风格和业务需求，而不是拿模板套住他们。** 全程零机械资产：候选 AI 检索、骨架 AI 生长、参考只事后照镜。

## 六步流程

### ① 读 V0.1
**模式判定（先于一切）**：调起方任务书带「**管线模式**」标识 → 按管线模式执行，**V0.1 路径必给，缺=停线报告**（禁降级成最小问答——丢了页面地图，比稿卡就没有代表页挑选池）；无标识且用户直接说"帮我选风格" → 独立模式（下述最小问答）。禁靠猜意图分模式。**外部协议优先**：任务书附**协议页**时，守门与登记口径以协议页为准（正本=主线 references/integration-contract.md）；无协议页按本文件原生流程。
§1 项目定义（**受众组**按"给谁用"分组：组名+谁+在那干什么；单组项目一组即全部）/§2 业务链路/§3 **页面地图**（主线页清单+行为叙述——代表页的挑选池，页怎么长不是你的活）/§4 功能刻度/§5 动效档。独立模式缺 V0.1 时补最小问答——**只问风格决策相关的三件事：给谁用（受众）/要什么感觉（气质）/什么设备（平台），每问带 2-4 个口语选项让用户点选，一次一问；禁开放式作文题，禁问产品功能与商业模式**（产品是什么从用户的话里能知道即可，够判断产品性质就行——需求调研不是你的活）。其中**气质/感觉是主观题**：用户答"说不准/都想看看"是常见且合法的回答，如实记录——文字描述不可决的维度，不逼用户做文字决策（交给比稿卡看图选）。

### ② 适配报告（每组受众一行）
**先翻译业务，再碰风格库**：把 V0.1 翻译成产品约束表——①产品性质一句话（交易工具/内容消费/情感陪伴…）；②使用场景与成败标准（从受众和链路推，例：全年龄段家庭聚餐=零学习成本+长辈可读+下单快）；③品牌层缺什么（文化定位/品类）——**缺了先问用户补齐再检索，禁自行条件分支硬猜**（例：连锁餐饮没说品类，"国潮"就不是候选而是待问项——沙县用国潮是笑话，塔斯汀用国潮是身份）。之后检索与扩散对照约束表逐卡判断；品类气质联想（餐饮→烟火气、中式→国潮）不是适配理由——风格服务于产品的任务与认知习惯，不服务于品类的氛围想象。
候选风格清单：**相关的卡全部列出**——扩散池里判断能服务约束的都算，禁只列自己想要的、禁设"落选说明"式的淘汰坟场。每张写：为什么相关（落到约束表某一条）+ 短板或硬冲突 + 适配点；深读过的写九段实据，未深读的如实标注"仅一句话初筛、点名即补读"。**AI 给推荐排序**（首推/对照/存疑分档，写明取舍意见）+ 比稿规模建议（数量不写死）——推荐是意见不是门槛，选权全在用户。**深读卡点**：首推组的卡必须先深读 prompt.md（九段正本）再写进报告；manifest 一句话只配初筛，禁单独作推荐依据。**气质答"说不准/都想看看"时**：不按气质筛候选——各气质方向各 1-2 张全部进池，比稿卡承担最终收敛（用户看图选）；比稿规模建议分档给出（精简版/全方向版）由用户拍板。候选来源：**wiki 检索优先**（见 references/wiki-access.md——源探测+扩散→收敛协议）；wiki 缺位→flow-ux-ui-line-cy-hifi-design 九槽兜底；**AI 自创=彻底没有了才用**。惯例风格（如"后台就 ant"）用户明示才成立，AI 不默认。

### ③ 用户拍板比稿配置
选哪些风格、几稿、谁多稿。同风格多稿启用与否由 AI 在报告中建议。
**比稿池硬卡点**：池清单呈用户 → **拿到用户的确认文字（如"就要 1234"/"678 也要"）才算拍板**。呈报、检索、点名、加批讨论都属讨论阶段——**讨论阶段禁做任何派工准备动作**（复制参照/读比稿规格/派子代理全禁）；未拍板先动手=越权，立即停并交代现状。
**用户点名某风格时**（含检索漏掉、库里其实有的）：产出 = 按**风格提示词起草协议**（solo-ui-line-cy-style-to-hifi-gui `references/prompt-protocol.md`，正本=solo-tool-line-cy-wiki-card-gen 04-prompt）**原创起草该风格的项目适配提示词**（前言+九段，适配本项目受众与业务）——库卡（card.md 九段）是参考素材之一，**禁照卡换色板交差**（映射≠起草）；起草稿呈用户过目，确认后入池。

### ④ 子代理并行比稿
每个候选一个子代理（诠释差异=比稿价值的一部分），组间并行（比稿无数据依赖）。**派发模式（铁律）：子代理一律后台模式（run_in_background）派发——主会话保持可对话，用户插话不杀代理；回执靠完成通知回收，禁前台阻塞等待。**子代理产出**比稿卡**（规格见 references/specimen-card-spec.md）：带颜色带情绪的骨架图集（3-5 个代表页，AI 从 0.1 §3 页面地图挑最能拉开风格差异的页）。完成定义含**渲染实看**：子代理交付前自己看渲染图，静态自查不替代；任务书禁写"禁截图/统一检验"式条款。生长公式：**风格 × V0.1 = 布局**——骨架随风格基因生长，禁查模板库（extract 九类仅事后照镜查常识）。主进程把各卡拼成合集页（多卡并排，file:// 直开）。

### ⑤ 用户选
多选一/多选（比稿数量按③拍板的配置——数量不写死；多选时同族共享 DOM、异族各成套——套数管线推导，用户不选套数）。交互纪律：
- **话语一等公民**：用户说什么都听，分诊处理——风格情绪类（"调暖一点/没感觉"）→ 当场对话微调或换候选；内容结构类 → 登记需求变更回主流程，重大则回炉；
- **微调定稿必须落进提示词副本**：风格情绪微调当场改的是样张——定稿后把微调内容**改写进项目内的提示词副本**（`specimens/<卡id>/prompt.md` 对应段落），改稿呈用户确认；确认后的副本=下游画图的唯一风格定义。**wiki 母本永不改**（全库共用资产，改母本=污染所有项目）——禁"样张是微调版、提示词还是库卡原版"的双轨漂移；
- **混搭请求**（"结构要 B 颜色要 A"）→ 重生长为新候选 D 再选，禁手工拼装；
- **重出**：可指定保留（"留第二张换另两张"）。

### ⑥ 回传确定值
按 references/selection-contract.md 写 `intake/selection-result.json`（选中清单含 skeletonTokens 最小集+骨架描述+确认记录）。**风格提示词副本=微调定稿版**（发生过对话微调的，随 selection-result 传递微调后的副本路径——下游画图与编辑版转化以此为准，禁传库卡原版）。skeletonTokens 的键名逐字照 references/token-minimum.md（正本在主技能 assets/token-keys.json，一律全小写连字符），值的来源见 references/token-minimum.md「取值」。多选时的族/骨架归属，写入前按四个方面（信息密度、元素粒度、布局范式、内容分布）逐个风格列给用户确认——规则见主技能 references/editor-runtime.md「AI 判族」。**失败宁停勿错**：重出一轮仍不收敛 → status=failed + reason，停线报告，不猜默认风格硬推进。

## 铁律

1. **只读 V0.1、只回传确定值**——不改开工文档，合并权归主技能；
2. **内容两防**（比稿卡）：防扣字眼（内容故意不含项目信息）+ 防偷懒（禁 lorem/禁"这里是文字"式空话）——图片一律色块占位；
3. **风格载体真实级**：真色板/真字体渲染/真组件形态/真图标族——批评面来自内容仿真，情绪传达来自风格载体，两者分离；
4. **令牌是记录不是枷锁**：skeletonTokens（references/token-minimum.md）照常回传，定位=选定风格的取值记录（供主技能装入开工文档、编辑版转化时参考）——不锁画面、不约束任何环节的自由绘制；
5. **先比稿后快捷**：任何"惯例捷径"（含脚手架直出）都需用户明示；选到大厂 UI 脚手架且用户要"直接工程"→ 回传 pipeline=scaffold 停线（该管线另行开工，当前版本不执行）。
