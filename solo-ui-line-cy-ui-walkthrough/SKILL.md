# solo-ui-line-cy-ui-walkthrough — 零截图确定性 UI 走查

## 前置条件

- Node ≥18；design-audit 引擎库（脚本按顺序解析：环境变量 `DSH_DESIGN_AUDIT_LIB` → 本机 profile → workspace 克隆；都找不到时退出码 2 并提示安装）
- 会话具备页面截图与读图能力时，观感评审层可用；不具备则该层跳过并在报告声明

## 铁律（全程有效，违反即返工）

1. **零截图**：机检取证只读几何与计算样式，不产生图片文件；观感评审的截图仅允许写入系统临时目录、评审后即删，禁止进入交付目录与技能目录
2. **输出纪律**：全量数据只落盘（台账 json/md）；模型只读末尾 ≤10 行摘要与严重问题清单——脚本进度日志供人排查，不进模型上下文
3. **完成由退出码裁定**：重跑探针非零 = 存在未裁决或未修复的 P1（已仲裁驳回的误报项自动豁免，不计入）；禁止口头宣称"修好了"。**限定**：退出码只覆盖脚本机检层（P0/P1 同卡，且错误页必须为 0——batch.mjs 错误页>0 即 exit 2）；观感评审与仲裁新增条目不进重跑台账，以台账状态人工确认闭环，compare 的「已修复」对它们不作数
4. **外部协议优先**：任务书附**协议页**时（如主线 flow-ux-ui-line-cy-hifi-design 管线调起），问询与登记口径以协议页为准（自动模式下启动问询转待确认包并标「未确认·自动通过」，锁定单按主线条目代答）；无协议页按本文件原生流程。

## 启动流程（第0问 → 两问 → 场景菜单 → 修复选择；锁定后进主流程）

技能触发后先输出欢迎块（话术见 onboarding.md §启动欢迎），然后依次：

- **第0问 要走查的页面在哪里？**
  发目录、单个文件或网址都行；工作区里有多个候选目录时，**列出来让用户挑**，不自作主张
- **问① 有没有设计系统？**
  有 → 严格模式：间距刻度/令牌按契约白名单**违规级**组装
  无 → 一致模式：事实基线（统计主流值为基线），离群报建议级，报告头注明"立场为推断"
- **问② 要不要用 AI 识图能力？**（先自检：会话具备截图与读图能力才问此题；不具备 → 提示"当前会话不支持识图"，按「不用」处理，不问）
  用 → 可选评美观/构图/层级
  不用 → 只用脚本查几何/字号/间距等硬指标；错误分析仍由 AI 做
  （菜单过滤是系统内部行为：问与选项里**禁止解释**"菜单会隐藏/全显"这类机制——用户看到菜单自然明白）
- **【弹出场景选择菜单】**（每项标注耗时与覆盖，点选即定；保留原编号）：
  1. UI 脚本（几何布局/遮挡/Z轴/换行/字号/间距/资源健康）——快扫，几分钟
  2. UI 脚本 + 观感评审（AI 读图）〔问②=不用识图时隐藏〕
  3. UI 脚本 + 文字内容检查（AI 参与分析，不看图）
  4. UI 脚本 + 观感评审 + 文字内容检查〔问②=不用识图时隐藏〕
  5. UI 脚本 + 交互完整（触控/表单/列表/弹层 + 路由完整）
  6. 全选——勾选当前菜单全部可选项（用识图时=全量；不用识图时=1+3+5）
  7. 深度走查——UI 脚本 + 界面六轴深检（solo-ui-line-jk-deep-review：排印/文案/无障碍/布局/颜色/打磨，输出按严重度排序的深检报告）——覆盖最全，耗时随页数增长
  ▸ 自定义：用**多选问题**把全部能力按域分组列出（脚本机检各探针组 / 观感评审 / 文字内容 / 交互完整 / 路由 / 动效），让用户**逐项打勾**——禁止让用户打字描述想要什么；自定义清单与菜单应用同一过滤规则
  （菜单注：不用识图时「文字+交互」组合直接选 6，无需走自定义）
- **问③ 检查出的问题是否修复？**（决定中间是否还有人工参与）
  1. **按照 AI 诊断内容直接修复** → 仲裁后连跑规划/派发/修复/复验，中间不停
  2. **只输出报告** → 仲裁完成后交付，修复另起
  3. **仲裁后暂停确认** → 仲裁完成输出**修复任务单（按子代理逐个列分工：谁修哪些页面/哪些文件/什么修法）**，用户确认后才派发；确认后修复与复验连跑不停
- **【配置锁定单】**（问③答完即输出，格式固定，字段不许增删）：
  ✅ 配置已锁定
  · 走查对象：<路径或网址>（形态：本地目录｜单文件｜线上网址）
  · 设计系统：<有→严格模式｜无→一致模式（事实基线；报告头注明"立场为推断"）>
  · AI 识图：<开启｜关闭（含识图选项已隐藏）>
  · 走查场景：<所选编号与场景名 + 能力组合>
  · 问题处理：<直接修复（仲裁后连跑修复与复验，中途不停）｜任务单确认后修复（仲裁后停，确认才派发）｜只输出报告>
  · 校验口径：缺省口径静默套用（字号下限/触控硬线/间距刻度；项目差异经 --caliber 注入，不展开参数）
  · 修复层：<连跑｜跳过（线上网址或只输出报告时）>
- **[边界]** 输入为线上网址时，问③ 固定为**只输出报告**（无源码可修）
- **[口径]** 一律从 config/caliber.json 缺省读取，项目差异经 `--caliber` 参数注入——不询问用户，不改技能内缺省文件
- **[交互方式硬规矩]** 所有问题一律用**选项**呈现（单选/多选打勾），用户只动手点；唯一需要打字的是第0问的路径。无交互界面的纯文本环境退化为「回复编号」，视为合规。禁止把选择题变成打字题，禁止使用"归因/机检/探针组"这类内部术语当选项文案

## 主流程（六步编排）

- **第〇步 输入识别**：目录 / 单文件 / URL / dev server / 带 query 本地路径 → 按 scenarios.md §场景路由决定直取或起本地静态服务；线上网址 → 标记"仅走查"，修复层跳过
- **第一层 机检取证**：`node scripts/batch.mjs <base> <root> <out> [--caliber 项目口径.json]` 全量机检 + 观感评审（AI 读图，按问二）；批量前先用 `scripts/fixtures/flawed.html` 跑单页冒烟验证引擎链路（浏览器可用性 see execution-pitfalls.md 速览）
  → 台账；finding 两态：`fix_certainty: 具体修法` 或 `仅问题区域（子代理自行评估）`
  → 空壳检测（元素 <20 标记）→ 可疑页进深探优先队列
- **第二层 台账仲裁（AI）**：读台账与证据包，逐条定性——证据充分的直接定级确认；存疑的**自主复核**（读源码/单页重探/截图）
  → 产出已仲裁台账（确认 / 驳回 / 需人决策）；对账等式：原始 findings = 分级 + 豁免 + 备注（不平打回）
- **[修复方式已由问③锁定]** 直接修复 → 仲裁后连跑第三至五层，中间不停；只输出报告 → 第二层完成后交付。线上网址固定为只输出报告。
- **第三层 规划派发（AI）**：按已仲裁台账聚类（共享层 / 模板级 / 单页）→ 修复任务分解 → 派发子代理（**一律后台模式**——用户插话不杀修复代理，完成靠通知回收）
- **第四层 子代理修复**：有具体修法的照改；仅问题区域的自行评估修法（依据契约与设计规范），改完自验
- **第五层 复验**：`node scripts/batch.mjs … --compare 旧台账.json` 重跑 → 已修复/仍存在/新引入 → 改动报告

## 深检路由（场景 7 或用户点名时启用）

- **六轴深检**：机检与仲裁完成后，调 `solo-ui-line-jk-deep-review` 对同批页面做排印/文案/无障碍/布局/颜色/打磨六轴深检（读源码按规则审，输出按严重度排序的报告），与机检台账合并交付；只报证据确凿的硬伤，品味分歧不入报告
  - 维度分工：机检管几何/字号/间距/资源健康等确定性硬伤；六轴深检补排印细节、界面文案、无障碍 WCAG 等语义维度——互不重叠，不重复消耗
  - 完成裁定不变：退出码仍只覆盖脚本机检层；六轴报告为附加交付，不入重跑台账
- **动效精修路由**：用户要求动效专项时按序调 emil 三件套——`solo-ux-line-emil-ui-remove-motion`（删多余动效）→ `solo-ux-line-emil-ui-review-motion`（专家评审）→ `solo-ux-line-emil-motion-choreograph`（多元素编排）；动效设计约定仍归 solo-ux-line-X-add-motion-design
- 两类深检均为**按需扩展**：菜单未选 7 且用户未点名时不自动执行

## 执行纪律（播报与中断）

- 每层开始与结束各向用户播报一行进展（如：第一层机检取证完成——83 页，发现 176 条）
- **引擎熔断**：首个页面报引擎错误（调试端口超时/导航失败/浏览器未起）→ **立即停止全量扫描**并转排障（核查浏览器可用性，可用 `DSH_DESIGN_BROWSER` 指定候选），修复后重跑；禁止带故障烧完全量——每页 25s 超时 ×N 页全是空转，且全错误页可能以 exit 0 收场
- 用户可随时喊停：机检层立即停（逐页落盘不丢）；仲裁层停后已裁决条目有效；修复层在子代理边界停（已派出的跑完自验，未派出的取消）——绝不留下改一半的文件

## 铁律补遗（修复段）

- 修复按**根因聚类**执行（共享层一处修全站 → 模板级 → 单页），禁逐条乱序
- **修复派发三形状**（按序执行，勿按页面竖切多代理）：① 脚本层——确定性注入（sr-only h1/焦点环/令牌等）由主代理直接脚本执行；② 判断代理——需逐选择器甄别的（信息/装饰灰字、aria 语义、alt 描述）交 1~2 个子代理；③ 专项微修——个位数文件主代理顺手做。「≤30 页/代理」仅是**扫描**分片上限，不适用于修复
- 任务书发**成品改动清单**（精确到选择器）优先于修法配方；镜像树（2×）同步走脚本变换（px×2），禁手抄
- 数据塌陷类病因：禁改样式掩盖，修数据/模拟层（归因卡已定类的照类执行）
- 子代理间禁改同一文件；共享层改动由主代理统一执行
- 一切 finding 形态产出（正式走查、试跑、抽查、机制测试）未入台账并过仲裁定性，一律为候选证据，禁止据此触发修复或产物改动
